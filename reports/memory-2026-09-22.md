# Static RAM report — µnleashed BBS 0.21.1

Date: 2026-09-22
Previous report: `reports/optimize-2026-09-20.md` (0.17.2).
Nothing was built, changed, committed or flashed. Every figure below comes
from the existing `.pio/build/esp32dev/` artefacts.

---

## 0. The headline

**4,776 bytes of static DRAM remain. That is two thirds of one caller node.**

Two days ago it was 34,360. Forums, the unified composer and the identity
work spent **29,584 bytes**, which is 86% of the entire margin, in one
milestone.

The previous report's top recommendation (B1, `BackupService` off `.bss`,
12,192 bytes) was not acted on. Had it been, today's headroom would be
16,968 and this report would be routine. It is now the difference between
the roadmap fitting and not.

### The ceiling

`memory.ld`: `dram0_0_seg (RW) : org = 0x3FFB0000, len = 0x2c200`.
`sections.ld` asserts `_bss_end - ORIGIN(dram0_0_seg) <= LENGTH(dram0_0_seg)`.
So the enforced limit is **180,736 bytes**.

```
3ffb0000 A _data_start
3ffb5764 A _data_end      -> .dram0.data  =  22,372
3ffb5768 A _bss_start     (4 bytes lost to alignment)
3ffdaf58 A _bss_end       -> .dram0.bss   = 153,584
3ffdaf58 A _heap_start
```

| | bytes |
|---|---:|
| `.dram0.data` | 22,372 |
| alignment `_data_end` → `_bss_start` | 4 |
| `.dram0.bss` | 153,584 |
| **consumed (`_bss_end - 0x3FFB0000`)** | **175,960** |
| **ceiling** | **180,736** |
| **headroom** | **4,776** |

**97.4% of static DRAM is in use.**

PlatformIO prints **53.7%**, because it divides `.dram0.data + .dram0.bss`
(175,956, which is the true figure minus the 4 alignment bytes the linker
also charges) by 327,680. **Multiply PlatformIO by 1.81.** 55.3% on its
scale is the wall.

Flash: `firmware.bin` is 1,133,744 of a 1,572,864 slot = **72.1%**, with
439,120 free. Flash is not the constraint and nothing in this report is a
flash recommendation.

### 1. The backup window is 20,368 bytes of permanently resident DRAM for a feature that is switched off

**Carried from 2026-09-20 (findings B1 + B2 + B3), not acted on. It has not
shrunk and the board can no longer afford to leave it.**

| Symbol | bytes |
|---|---:|
| `Bbs::backup_` (`BackupService`, offset 4 in the singleton) | 12,192 |
| `users::validateFile(...)::seen` (`char[250][21]`, `users.cpp:502`) | 5,250 |
| `users::validateFile(...)::u` (scratch `UserRec`) | 492 |
| `core/ziparc.cpp.o` total (`open::tail` 1,046, `open::raw` 256, `open::norm` 256, `extract::probe` 310, `extract::cfgProbe` 310, rest) | 2,434 |
| **total** | **20,368** |

`BackupService` measured from DWARF:

| member | bytes |
|---|---:|
| `exp_` (`ziparc::ZipExport`: `list_[66]` 3,168 + `manifest_[1536]` + `line_[176]` + `hdr_[96]`) | 5,016 |
| `imp_` (`ziparc::ZipImport`: `items_[64]` 3,584 + `zipPath_[96]` + `ImportReport` 180) | 3,872 |
| `hdr_[1536]` HTTP request header | 1,536 |
| `out_[1024]` response buffer | 1,024 |
| `summary_[128]`, `detail_[112]`, `notes_[6]` 438, scalars | 744 |
| **total** | **12,192** |

**11.6% of the entire static budget, resident from boot to reboot**, for a
feature that needs the BOOT button held *and* a sysop logged in, then runs
for `backup_window_minutes` (default 5). Most boards will go their whole
life without it opening once.

**What to do.** Allocate the whole thing when the window opens; free it when
it closes. This is not "use the heap" as an architecture change: `CLAUDE.md`
already records the exception ("temporary inflate buffers during a backup
upload"), it is the same feature, the same lifetime, and it is outside the
caller loop in exactly the same way. Nothing in `tick()` changes.

**What it gives up.** If ~20 KB contiguous cannot be had, the window does not
open and the sysop gets a message instead of a port. That wording matters:
"not enough memory right now, try with fewer callers on", not a hex address.
Heap free at boot was measured at roughly 78 KB at 0.17.0 and static has
grown 29.6 KB since, so a rough estimate today is 48 KB free with a smaller
largest block. **That is an estimate.** `MEM` already prints
`heap_caps_get_largest_free_block`, so confirm it on the board before this is
relied on, and log the requested size beside the largest free block on
failure so "fragmented" is distinguishable from "full".

**Three cheaper variants, in order of how little they ask for:**

- **`exp_` and `imp_` are a union.** `BackupService::St` is one enum and one
  client is served at a time, so a request is a download or an upload and
  never both. **3,872 bytes, no heap, no behaviour change**, and the
  invariant is already enforced by the state machine. If only one thing on
  this page gets done, do this one.
- **`seen[250][21]` becomes 250 32-bit hashes.** 1,000 bytes instead of
  5,250: **4,250 saved.** A hash match is not proof, so on a match re-read
  the file to confirm, which happens only when the file really does contain
  a duplicate, during an upload, once.
- Both together: 8,122 bytes with no heap at all, which is 1.7× the current
  headroom.

**How you would know it went wrong:** the window refuses to open on a busy
board, or a restore that used to work now reports a failed allocation.

### 2. Twenty-two `static UserRec` scratch buffers, 10,332 bytes, and this one is growing

**Where:** 22 distinct 492-byte symbols. `bbs.cpp` 4, `bbs_sysop.cpp` 3,
`bbs_users.cpp` 7 (which is that object file's entire DRAM footprint,
3,444 = 7 × 492), `users.cpp` 8. One of them,
`users::validateFile::u`, is counted under #1, so the figure here is
**21 × 492 = 10,332**.

**It grew 2,580 bytes in two days and nobody would have seen it.** Last
report: 17 × 456 = 7,752. Today: 22 × 492 = 10,824. Two growth vectors at
once — more of them, and `UserRec` itself went 456 → 492 when 0.19.0 added
`id`, `retired`, `staffAt`, `staffLevel` and `staffIp[16]`. **This is
precisely the figure that is invisible in one report and obvious across
two.**

The corollary is worth pinning up: **`UserRec` exists 34 times in DRAM** —
22 statics plus `Session::edit` × 12 — so **every byte added to `UserRec`
costs 34 bytes of static DRAM, not one.** A 16-byte field is 544 bytes. That
should be said out loud before anything else is added to an account.

**Why they are static.** The comments say so: `// static: off the task
stack`. That was a reasonable instinct and the evidence now says it is
over-applied.

- `BBS_TASK_STACK` is **8,192**, and it is **heap**, not `.bss`.
  `xTaskCreatePinnedToCore` → `pvPortMallocStack`, which IDF 5.3.1 defines
  as `pvPortMalloc` (`freertos/FreeRTOS-Kernel/include/freertos/portable.h:191`),
  i.e. `heap_caps_malloc`. So a static → local conversion moves bytes off
  the 180,736 budget entirely. It is not new memory; the 8 KB is already
  paid for whether it is used or not.
- **That stack already carries a 1,729-byte frame.**
  `src/plugins/forums.cpp:1247` is `char body[kBodyMax + 1];` inside
  `showMessage`, on the caller's own path, plus `line[160]` and `head[96]`.
  It works. A 492-byte frame is less than a third of that.
- **Three of the 22 are in disjoint scopes of one function.**
  `Bbs::formSave(...)::cur` appears three times at `bbs_users.cpp:342, 356,
  397`. As statics that is 1,476 bytes; as locals the compiler overlaps
  disjoint scopes into one slot, so that function alone goes to ~492 on the
  stack.

**Do it in two tranches, and the first one is nearly free.** The eight in
`users.cpp` (`lookup`, `count`, `at`, `maxId`, `range`, `add`, `update`,
`retire`) are leaves: they call stdio and nothing that allocates a `UserRec`.
Converting those alone is **3,936 bytes** at negligible nesting risk. The
fourteen in `bbs*.cpp` sit in command handlers that can call into `users::`,
so the worst realistic path is about two nested records, ~1 KB.

**What it gives up.** Task stack depth. The failure mode is a stack overflow,
which on this board is a panic rather than silent corruption
(`CONFIG_FREERTOS_CHECK_STACKOVERFLOW` is on by default in IDF 5.3.1), so it
would be loud and immediate rather than a mystery three weeks later.

**How you would know it went wrong, and this is the part that makes the
recommendation safe:** put `uxTaskGetStackHighWaterMark(nullptr)` on the
`SYS` screen, next to the loop figures that are already there. The board then
*says* how much stack it has never touched, before and after, instead of
anybody reasoning about it. The project already learned this with
`esp_wifi_get_ps()`: the cure for two wrong confident answers was not more
care, it was making the board report.

Measure first, convert second. If the high-water mark says 6 KB has never
been touched, this is a morning's mechanical work for 10 KB.

### 3. The form context and the message composer are never live at the same time, and each session carries both

**11,856 bytes**, or 5,928 for the lower-risk variant.

Per session:

| member | bytes | used by |
|---|---:|---|
| `compose[1153]` | 1,153 | chat mail, forum posts, feedback later — `SState::Plugin` only |
| `edit` (UserRec) | 492 | core forms — `SState::Form` / `UserList` |
| `fields[16]` | 320 | core forms |
| `form` | 176 | core forms |
| | **2,141** | |

A union is `max(1153, 988) = 1,153`, saving **988 per session = 11,856**.

**The exclusivity checks out, and I checked it rather than assuming it:**

- `compose` is written only from `chat.cpp` (1771, 1813, 1825, 1829) and
  `forums.cpp` (1428, 1473-1476, 1639-1646, 1839, 1901). Both require the
  plugin to own the session, i.e. `SState::Plugin`.
- `grep '\.form\b|\.fields\b|\.edit\b' src/plugins/*.cpp` returns **nothing**.
  No plugin touches the form storage at all.
- `edit`/`fields`/`form` are driven only from `bbs_users.cpp:228`,
  `bbs_sysop.cpp:1256` and `:1390`, all of which set `SState::Form`.
- A caller in a form is not plugin-owned, and a plugin-owned caller is not in
  a form. `Bbs::own()` and the form entry points are the two ways in and they
  are different states.

**`Session::edit` is also doing less than its name suggests.** There are 56
references to `s.edit` in the whole tree, and of the named-field accesses
`handle` is 20 of 34. The session-lifetime fields are **already mirrored
elsewhere on the Session**: `edit.handle` → `s.user` (`bbs.cpp:1209`),
`edit.level` → `s.rank` (`:1549`), `edit.dayMinutes` → `s.dayUsedMin`
(`:1541`). That mirroring was not accidental; the 0.8.0 code review
deliberately made `formSave`, `cmdInfo`, `saveCallStats` and the rest
**re-read a fresh record** rather than trust `s.edit`, which is exactly why
there are 22 scratch statics in finding #2. So `edit` is a form buffer that
happens to survive the form, and the four or five fields read outside it are
already duplicated.

**What it gives up, and this is the honest part.** The invariant "form state
and composer state are never simultaneously live" is *precisely* the shape
this project has been bitten by twice: `owns()` answering two questions in
chat (0.17.12), and one field holding both a forum's message total and a
caller's unread count (0.21.0). **When a name could mean two things, it
eventually does.** A union that is wrong by one code path corrupts a caller's
half-written message or their half-filled form, and it will do it rarely and
look like the board being flaky.

So it needs the invariant made explicit rather than assumed: a `uint8_t
scratchOwner` on the Session naming which subsystem holds the storage, set on
entry to either, cleared on exit, and checked on entry to the other. A
mismatch is a refusal with a message, not silent reuse. That guard is about
twenty lines and it is what turns this from clever to safe.

**Lower-risk variant, half the bytes, no invariant at all:** `edit` +
`fields` + `form` (988) come from a **pool of six** claimed on form open
instead of one per session. **5,928 bytes.** Filling in a form is a shell
activity a caller does for thirty seconds; six at once on a ten-line board
is a board having a very good day, and the seventh gets "too many people are
filling in forms, try again in a moment" — a refusal the board already makes
for CONFIG (one at a time) and for file transfers (one board-wide). The
failure mode is a message, not corruption.

**If only one of #2 and #3 is taken, take #2.** Its failure is loud, its
guard is a number on a screen, and it is 10 KB.

### 4. The CONFIG editor holds 3,904 bytes permanently for an editor that is explicitly one-at-a-time

**Where:** `src/core/bbs_sysop.cpp:893-897`.

| Symbol | bytes |
|---|---:|
| `g_cfgBuf[16][96]` | 1,536 |
| `g_cfgWas[16][96]` | 1,536 |
| `g_cfgSum[16][28]` | 448 |
| `g_cfgKeys[16][24]` | 384 |
| **total** | **3,904** |

`g_cfgOwner` is a single `const Session*` and the code refuses a second
editor with "`<handle>` is editing the settings" (`:1148`). So this is
resident from boot for something that at most one sysop uses, occasionally,
for a minute. Same shape as #1 and the same answer: allocate at `CONFIG`,
free at save or cancel, refuse with a message if the memory is not there.
Add `g_subBuf[8][64]` (512) and `g_cfgPlugin` and it is nearer 4,600.

**And there is a free 1,472 bytes in it that needs no heap.** `g_cfgWas`
exists for exactly one purpose: `configSave` does
`if (!strcmp(v, g_cfgWas[i])) continue;` (`:1276`) to write only what
changed. A **32-bit hash per field is 64 bytes**, saving **1,472**, with no
allocation, no lifetime question and no behaviour change.

It also removes a bug class permanently. `g_cfgWas[i]` was filled with
`"%.47s"` into a 96-byte buffer, so **any value longer than 47 characters
compared unequal to itself and was rewritten on every page save whether or
not it had been touched**. That shipped, and it is fixed at `:1218` now by a
`%.*s` with the right width — but a hash computed over the whole value
cannot have that bug at all, because there is no width to get wrong.
Announce's comma-separated `servers` list is exactly the long value the 96
byte buffers exist for.

**What it gives up.** The hash variant: a 1-in-4-billion chance that an
edited value is treated as unchanged and not written. For a sysop typing in
a settings form, that is not a risk, it is a rounding error, and the sysop
sees the old value on the next page open.

### 5. `SubjRow` caches 3,328 bytes of subject text the card is already holding

**Where:** `src/plugins/forums.cpp:860-878`.

```
struct SubjRow {
    uint32_t hash, newest, unread, total;   // 16
    char     subject[kSubject + 1];         // 52
};                                          // 68
SubjRow g_subjRow[kMaxSubjects];            // 64 rows = 4,352
```

The table is already the good design: **one board-wide, tagged with the
caller and the forum that filled it**, with a comment explaining that
per-session tables would have been 53 KB. That decision stands and nothing
here disturbs it.

What is left is that **52 of the 68 bytes per row are a copy of text that
lives in `INDEX.TXT`, where the offset of message N is N × 128 arithmetic.**
Keeping the hash and the three counters (16 bytes) and reading the subject
back when a row is actually drawn saves **64 × 52 = 3,328 bytes**.

**The precedent is this project's own and it is stated in `CLAUDE.md`:**
file descriptions are "`FILES.BBS` in each folder... **Read on demand rather
than cached**: a folder of two hundred files would be a 12 KB table on a
board whose heap is in tens of KB, and rereading the file per row costs
nothing that matters". The identical argument applies here, and here it is
better, because a forum index is a fixed-stride file and needs one `fseek`
and one 128-byte read, not a linear scan of a text file.

**What it gives up.** One seek and one 128-byte read per *drawn* row, which
is at most a screenful, not per scanned record. The scan itself
(`kScanMax` 2000 records) is unchanged.

**Watch for the interaction with the 126 ms stall.** `CLAUDE.md` records a
measured 126,146 µs worst loop pass attributed to synchronous card work on
the caller's path, and this adds card reads to a listing. Against that:
these are 128-byte reads at known offsets, which is the cheapest thing SDSPI
does, and the same change removes 3.3 KB from a board with 4.8 KB left. If
the loop instrumentation shows it, the answer is to read the whole visible
page in one pass rather than to put the cache back.

**How you would know it went wrong:** `SYS` reports a higher worst pass with
`doing` naming a forums verb. The instrumentation to see that already
exists, which is the point of it.

## 3. Sixth item: does the queued work fit?

**No. Not as the board stands today.**

| | static DRAM |
|---|---:|
| headroom today | **4,776** |

Estimates for the three queued items, with the reasoning shown. None of
these are measurements.

**CONFIG PALETTE colour editor — near zero, if it stays board-wide.**
It is a `CfgField` table (const, flash) reusing `g_cfgBuf` and friends, which
are already resident, plus the palette itself: 12 to 20 `Color` values at one
byte each. **Call it 100 bytes.** It fits with room to spare.

There is one way to make it expensive, and it should be said before somebody
does it: **a per-caller theme stored in `UserRec` costs 34 bytes per byte**,
because `UserRec` exists 34 times in DRAM (22 statics + 12 `Session::edit`).
A 16-entry palette per account is **544 bytes**, or 11% of the entire
remaining headroom, for a preference. A per-caller theme read from the card
into a per-session `uint8_t` index into board-wide palettes costs 12 bytes.
Same feature, 45× the difference.

**Ten information pages — near zero, if they are screens.**
`ScreenPlayer` is already per session and already streams from card or flash;
ten more files cost flash or card space and nothing in DRAM. A menu is a
const table. Add a `uint8_t` per session to remember which page: **12 bytes,
plus a const table in flash.** It fits.

If instead they are held in RAM to be searched or listed dynamically, the
cost is whatever they are, and the answer is that they should not be.

**Mail as a subsystem — 4 to 8 KB, and this is the one that does not fit.**
The honest comparison is what the two comparable subsystems actually cost in
this build: `forums.cpp.o` is 6,797 and `chat.cpp.o` is 3,148 (of which
mail's share is `g_mailTo` 1,344, `g_mailAt` 256, `g_mailFl` 64, the
per-session reading context `g_mailMode`/`g_mailIdx`/`g_mailRoom`/`g_mailWho`
at ~300, `g_writeTo` 264 and `g_writeCo` 144, so about 2,400 today).

A mail subsystem with folders, a larger index, a per-session reading context
and its own list machinery is forums-shaped, so **5 KB ± 2** is the honest
range. It should reuse `Session::compose`, which is what that buffer exists
for and which keeps 13.8 KB off the estimate; if it grows its own composer
the figure is 5 KB + 13.8 KB and the answer is not "it does not fit", it is
"that overflowed the board once already and is why `compose` was unified".

| | static DRAM |
|---|---:|
| headroom today | 4,776 |
| PALETTE (board-wide) | −100 |
| ten information pages | −12 |
| mail as a subsystem, midpoint | −5,000 |
| **remaining** | **−336** |

**So: PALETTE fits. The information pages fit. Mail alone consumes the entire
remaining headroom and then some**, and that is the midpoint estimate with
nothing going wrong and no margin for the next thing.

The wider point is not really about mail. **4,776 bytes is 2.6% of the
budget, and one caller node is 6,980.** The board has less headroom than one
node. The only lever available today without a code change is cutting a node,
which is exactly the trap `CLAUDE.md` already names: sixteen nodes failed by
~100 bytes and the node count was cut to fix the symptom of a different
problem.

**With recommendation #1 alone** (20,368), headroom becomes **25,144**: all
three fit with 20 KB spare.
**With #1, #4 and #5** (27,600), headroom becomes **32,376**, which is
roughly where the board was two days ago, i.e. back to a working margin
rather than a countdown.

**The trend matters more than any single line.** Headroom went 34,360 →
4,776 in one milestone, 86% consumed. That milestone was forums plus the
composer, both of which were planned and both of which were worth it. The
next one has no room to be worth anything, and that is the actual finding.

## 4. Also found, and these are defects rather than size choices

### 4.1 `announce` uses an `snprintf` return as a length, and both of its buffers can overflow on a fully configured board

**This is a real bug on a network-facing path, and it is reachable from
CONFIG.**

`snprintf` returns the length it **would** have written, not what it wrote.

`src/plugins/announce.cpp:306` — `g_bodyLen = snprintf(g_body, sizeof(g_body), ...)`
into `char g_body[512]`. Worst case, counted from the format string:

| part | bytes |
|---|---:|
| fixed JSON scaffolding | 149 |
| `version` | 6 |
| `name` (`kNameMax` 40) | 40 |
| `owner` (`kNameMax` 40) | 40 |
| `description` (`kDescMax` 120) | 120 |
| `host` (`kUrlMax` 96) | 95 |
| `port`, `nodes`, `busy`, `uptime`, `interval`, `tz` | 31 |
| `token` | 40 |
| `extra` (`share_activity`) | 39 |
| **total** | **560** |

**560 against 511 usable.** A board with its description, owner and host
filled in writes a truncated body and sets `g_bodyLen` to 560. The line above
it, `announce.cpp:114`, reads:

```c
constexpr uint16_t kBodyMax = 512;    // the payload never gets near this
```

**That comment is the claim, and it is wrong for exactly the board most
likely to have filled the fields in.** `CLAUDE.md`'s "~200 byte JSON payload"
is true for a board with short fields and false for a full one. This is the
third instance in this project of a comment asserting a fact that the code
does not hold, and being believed.

The consequence at the protocol layer: `Content-Length:` says 560 and 511
bytes follow, so the directory blocks waiting for 49 bytes that never come
and then sees the connection close. A directory that is strict rejects the
heartbeat; a tolerant one accepts a truncated JSON body it cannot parse.
Either way the board is silently delisted and the sysop has no way to tell
why.

**The same mistake one layer up is memory-unsafe.** `announce.cpp:323`
formats into `char g_request[kBodyMax + 256]` = 768. Headers are up to **318**
(119 fixed, plus path 95, host 95, version 6, Content-Length digits 3), plus a
body of up to 511 = **829 against 767 usable**. `g_reqLen` is then the
would-be length, and `announce.cpp:496` is:

```c
while (g_sent < g_reqLen) {
    ssize_t n = send(g_fd, g_request + g_sent, g_reqLen - g_sent, 0);
```

so the board reads **up to 62 bytes past the end of a static buffer and puts
them on the wire.** Verified by address: `g_request` is at `0x3ffd2b50`
size `0x300`, and `g_bodyLen` (`0x3ffd2e50`) then `g_body` (`0x3ffd2e52`)
sit immediately after it, so what leaks is a fragment of the board's own JSON
payload rather than anything sensitive. **Benign in content, still an
out-of-bounds read, and it is the mechanism that matters.**

**Fix:** clamp both, i.e.
`n = snprintf(...); g_len = (n < 0) ? 0 : (n >= (int)sizeof(buf) ? sizeof(buf) - 1 : n);`
and log once when truncation happens, because a silently short heartbeat is
indistinguishable from a network problem. Then size `g_body` from the field
maxima rather than from a guess: 560 rounded to 640, and `g_request` to
1,024. That costs 384 bytes of DRAM the board does not have today, which is
one more reason to take #1.

### 4.2 `kMaxParts = 8` is a hand-written bound over two tables, and it truncates silently

**Where:** `src/core/bbs_sysop.cpp:886`, used at `:1363`
(`for (i = 0; i < comp->count && i < kMaxParts && ...)`).

The composite counts themselves are now derived — `CFG_PARTS(t)` and
`kCompositeCount` are both `sizeof`-based, which is the 0.20.0 fix and it
holds. But `kMaxParts` is still a literal 8 sitting beside `kAreaParts` (6)
and `kTopicParts` (7), and `configSubSave` packs exactly
`min(comp->count, kMaxParts)` parts over whatever was in the file.

**Add a ninth part to either table and every save of that record silently
drops the last part**, which is bit-for-bit the bug that shipped when the
count was 4 against a six-entry `kAreaParts`: a staff-only download area
became downloadable by everybody and the board said "Saved and live".
`kTopicParts` is at 7 of 8. **One part of margin on a table that has grown
once already.**

The comment at `:886` even says it is "sized for the widest composite" —
which is a statement about a relationship that nothing enforces. Two
`static_assert`s, one per table, cost nothing and make it impossible:

```c
static_assert(sizeof(kAreaParts)  / sizeof(kAreaParts[0])  <= kMaxParts, "...");
static_assert(sizeof(kTopicParts) / sizeof(kTopicParts[0]) <= kMaxParts, "...");
```

**Fourth instance of this shape in this project.** It is no longer a bug, it
is a habit, and the general rule is worth writing into `CLAUDE.md` properly:
**a bound that stands beside a table must be derived from it or asserted
against it, never written out.**

### 4.3 `kBodyMax` (1728) and `BBS_COMPOSE_MAX` (1152) disagree about how long a forum post can be

`forums.cpp:519` sets `kBodyMax = 1728` ("24 lines × 72") and
`forums.cpp:1247` puts `char body[kBodyMax + 1]` — **1,729 bytes** — on the
BBS task stack in `showMessage`. But the composer that produces those bodies
is bounded by `BBS_COMPOSE_MAX` at `forums.cpp:1472`, which is **1,152**
("16 lines × 72"), and `appendBody` clamps writes to `kBodyMax` as well.

So **577 bytes of that stack frame can never be filled by anything this board
writes.** Not a correctness bug — `readBody` is given `sizeof(body)` and a
hand-edited body file would simply be truncated at 1,728 — but it is a buffer
sized for a number that no longer matches, and it is 577 bytes of the task
stack that finding #2 wants to spend more carefully. Settle on one number.

### 4.4 Documentation drift, both minor

- `CLAUDE.md` says `BBS_RX_ROOM` is 1 KB in the input-backpressure bullet;
  `src/config.h:105` says **1700**, which the 0.8.0 bullet in the same file
  gets right. Two different figures for one constant in one document.
- `CLAUDE.md` and `src/config.h:63` still describe a `Session` as 6,000
  bytes and the previous report corrected it to 5,716. **It is now 6,980**,
  so the documented figure is 14% low and the node-count arithmetic built on
  it understates twelve sessions by 11,760 bytes.

## 6. Reproducing this

```sh
TC=~/.platformio/packages/toolchain-xtensa-esp-elf@13.2.0+20240530/bin
GDB=~/.platformio/packages/tool-xtensa-esp-elf-gdb/bin/xtensa-esp32-elf-gdb.exe
ELF=.pio/build/esp32dev/firmware.elf

# the only RAM number that means anything
$TC/xtensa-esp32-elf-nm.exe $ELF | grep -E '_bss_end|_data_start'
# (_bss_end - 0x3FFB0000) against 0x2C200 = 180,736

# every DRAM symbol, biggest first
$TC/xtensa-esp32-elf-nm.exe --size-sort -S --radix=d -C $ELF \
  | awk '$1+0 >= 1073414144 && $1+0 < 1073590104' | sort -k2 -rn | head -40

# struct layout with padding holes
$GDB -batch -nx -ex "set pagination off" -ex "set max-value-size unlimited" \
     -ex "ptype /o struct Session" $ELF
```

Two traps that nearly produced wrong findings and are worth carrying
forward:

1. `nm` marks flash `.rodata` as `d`/`D` too. Filter every RAM figure by
   address to `0x3FFB0000 .. 0x3FFDAF58` or the mbedTLS curve tables look
   like RAM.
2. GNU `ld` attributes the whole merged string pool to the first object
   contributing a `.rodata.*.str1.1` section. If a future report says one
   source file owns ~100 KB of rodata, that is why.
