**Two measurement traps worth recording, because both nearly produced a wrong
finding in this report:**

1. `nm` reports `d`/`D` (initialised data) for symbols in *flash* rodata as
   well as DRAM. The mbedTLS curve tables look like RAM in an unfiltered
   listing and are not. Every RAM figure below is filtered by address to the
   window `0x3FFB0000 .. 0x3FFD3BC8`.
2. GNU ld attributes the **whole merged string pool** to the first object that
   contributes a `.rodata.*.str1.1` section. In this map that is
   `backup.cpp.o`, which appears to own 100,259 bytes of rodata. It owns 3
   (the map says so on the next line: `0x3 (size before relaxing)`). All
   rodata attribution below excludes `.str1.*` and reports the merged pool
   separately. If a future report says a single source file owns ~100 KB of
   rodata, this is why.

**Discrepancy found while establishing the baseline:** `src/config.h:55` says
`BBS_VERSION "0.17.1"`, while this milestone is 0.17.2. The measurements are of
whatever that build was; the version string appears not to have been bumped.

## 1. The real DRAM ceiling

PlatformIO's `RAM: 44.7%` is measured against 327,680, a number that
corresponds to nothing the linker enforces. The figure the linker actually
enforces is in the generated `sections.ld`:

```
  } > dram0_0_seg
  ASSERT(((_bss_end - ORIGIN(dram0_0_seg)) <= LENGTH(dram0_0_seg)),
          "DRAM segment data does not fit.")
```

and in `.pio/build/esp32dev/esp-idf/esp_system/ld/memory.ld`:

```
  dram0_0_seg (RW) : org = 0x3FFB0000 + 0,
                                     len = 0x2c200 - 0
```

So the rule is: **`_bss_end - 0x3FFB0000` must not exceed `0x2C200` =
180,736 bytes.** The 0x2C200 (176.5 KiB) rather than the 0x50000 the address
map would suggest is the ROM's own static data and stack sitting above it;
`memory.ld` says so in a comment.

Symbols read straight out of the ELF:

```
3ffb0000 A _data_start
3ffb4bb4 A _data_end        -> .dram0.data  =  19,380
3ffb4bb8 A _bss_start       (8-byte align, 4 bytes lost)
3ffd3bc8 A _bss_end         -> .dram0.bss   = 126,992
3ffd3bc8 A _heap_start
```

| | bytes |
|---|---:|
| `.dram0.data` | 19,380 |
| alignment to `_bss_start` | 4 |
| `.dram0.bss` | 126,992 |
| **consumed (`_bss_end - 0x3FFB0000`)** | **146,376** |
| **ceiling (`LENGTH(dram0_0_seg)`)** | **180,736** |
| **headroom** | **34,360 (33.6 KiB)** |

**The board is at 81.0% of its static DRAM, not 44.7%.** PlatformIO under-reports
by a factor of 1.81. A useful rule of thumb: whatever PlatformIO prints,
multiply by 1.81 to get the truth. 55% on the PlatformIO scale is the wall.

### Reconciling the sixteen-node failure

The 16-node build reported 179,972 static and failed with `dram0_0_seg
overflowed by 104 bytes`. Those two numbers do not agree with each other
(179,972 is 760 *under* 180,736), and they cannot be made to agree, because
PlatformIO sums `.dram0.data + .dram0.bss` while ld charges the region for
inter-section alignment and for every section mapped into it. The ld message is
the authority; the PlatformIO number was never measuring the same thing.

What does reconcile is the arithmetic, to within a couple of hundred bytes:

- 16 nodes is 18 sessions; today's 10 nodes is 12 sessions; the difference is
  6 sessions plus 6 more `Session*` in `all_[]`.
- At today's measured `sizeof(Session)` that is 6 × 5,716 + 24 = 34,320 bytes.
- 146,376 + 34,320 = **180,696**, which is 40 bytes *under* the 180,736
  ceiling.

So at today's code size, eighteen sessions would land within 40 bytes of the
limit — it would scrape in rather than overflow. The 104-byte overflow reported
at the time means that build carried roughly 150 bytes more non-session data
than this one does; I cannot account for that exactly without the failing
build, and I am not going to pretend otherwise.

The conclusion that matters is not the sign of the residual but its size:
**sixteen nodes failed by a hair, not by a mile.** It was ~100 bytes on a
180 KB budget. That is worth knowing for two opposite reasons. It means the
node count is recoverable from a very small saving — B3 alone, the 3,872-byte
`ziparc` union, would clear it many times over. And it means the node count
must **not** be raised on that basis, because DRAM was never the real limit:
finding A1 shows lwIP caps the board at 16 sockets in total, of which three are
always spoken for. **The node count is socket-bound, not RAM-bound, and cutting
16 to 10 fixed the symptom of a different problem.**

### `sizeof(Session)` is 5,716, not 6,000

Measured two independent ways: `ptype /o struct Session` reports
`total size (bytes): 5716`, and the `Bbs` layout shows `struct Session
nodes_[10]` occupying 57,160 bytes (57,160 / 10 = 5,716).

`src/config.h:63` and `CLAUDE.md` both say 6,000. The documented figure is 5%
high, which flatters the cost of a node by 284 bytes and overstates twelve
sessions by 3,408. Not a bug, but the node-count arithmetic in the `config.h`
comment is built on it.

## 2. Does what is coming fit?

Wanted: roughly 22–30 KB of static RAM for file transfer (~3.4 KB), message
bases (4–8 KB), mail, poker, the NeoPixel/RMT activity light, feedback, the
dashboard rework, and Wi-Fi credentials at runtime with Improv.

| | bytes |
|---|---:|
| headroom today | 34,360 |
| `CONFIG_LWIP_MAX_SOCKETS` 10 → 16 (finding A1, not optional) | −120 |
| **available** | **34,240** |
| wanted, worst case | −30,000 |
| **left over** | **4,240** |

**It fits, and nothing is left.** 4.2 KB of margin on a 180 KB budget is not a
margin; it is the next feature request away from another `dram0_0_seg
overflowed` and another capability being cut to fit, the way the node count
was.

With findings B1 and B2 taken (together ~16.4 KB, both from a feature that is
switched off almost all of the time):

| | bytes |
|---|---:|
| available after B1 + B2 | 50,682 |
| wanted, worst case | −30,000 |
| **left over** | **20,682** |

That is the difference between "fits" and "fits with room for the build after".

For sizing anything else: **one caller node costs 5,716 bytes of static DRAM
and one lwIP socket.** Today's headroom is six nodes' worth. After B1 and B2 it
is eight. The socket, not the DRAM, is the binding constraint — see A1.

## 3. Summary

Ranked by what it saves against what it gives up. **Caller-visible items are
marked.** The two categories are separate budgets: static DRAM is at 81% and is
the real constraint; flash is at 68.7% with 491 KB free in the OTA slot and is
not currently tight at all.

### Correctness — fix before sizing anything else

| # | What | Effect | Cost | Caller-visible |
|---|---|---|---|---|
| A1 | `CONFIG_LWIP_MAX_SOCKETS` is **10**, not the 24 asked for | 7 callers max, not 10 | +120 B static to fix | **Yes — the 8th caller is refused** |

### Static DRAM — the constraint

| # | What | Saves | Cost | Risk |
|---|---|---:|---|---|
| B1 | `BackupService` resident in the singleton → allocate when the window opens | **12,192** | one ~12 KB heap allocation on BOOT press; window fails to open if it cannot be had | Low |
| B2 | `users::validateFile`'s `seen[250][21]` → 4-byte hashes | **4,250** | one extra file pass on a hash collision, during upload validation only | Low |
| B3 | `ziparc` `exp_`/`imp_` union (a request is a download or an upload, never both) | **3,872** | none if the state machine invariant holds | Low |
| D1 | 17 scratch `UserRec` statics → a pool of 4 | ~5,900 | a slot-discipline bug corrupts an account record | **Medium** |
| D2 | Shrink `UserRec` itself (456 B × 29 instances) | 29 B per byte removed | fields callers can fill in | Product decision |
| D3 | `CONFIG` editor's 3,904 B of buffers, resident for a one-at-a-time editor | 3,904 | same shape as B1 | Low |
| E1 | `BBS_TL_BYTES` 3,072 → 2,560 | 6,144 | **the documented C64 type-ahead case** | **High — do not** |

### Flash — large, cheap, and not currently needed

| # | What | Saves | Cost |
|---|---|---:|---|
| C1 | `CONFIG_NEWLIB_NANO_FORMAT=y` | 25–50 KB (Espressif's figure; 76.5 KB of objects are present today) | no `%lld`, no C99 positional args. The board's own code uses neither |
| C2 | Disable the 11 unused mbedTLS ECC curves | est. 25–30 KB of the measured 34,638 | a future TLS peer on a non-P256 curve would fail |
| C3 | `CONFIG_ESP_WIFI_ENTERPRISE_SUPPORT=n` | est. 10–20 KB | no WPA2-Enterprise Wi-Fi, ever |
| C4 | `CONFIG_LWIP_IPV6=n` | est. 13–15 KB flash, ~1 KB DRAM | **no IPv6 callers** |
| C5 | Drop `sscanf`/`fscanf` (3 call sites) | 19,733 | none — subsumed by C1 |

### Nothing in the "20 KB for free" category on the flash side matters much

Flash is at 68.7% with 491,608 bytes free in the 1.5 MB slot. C1 and C2 are
each worth more than 25 KB for almost nothing, and they are worth taking — but
taking them does not unblock anything, because flash is not what is stopping
the next feature. **They buy OTA headroom and shorter web-installer downloads,
not features.** Said plainly, as the brief asks: on the RAM side there is
exactly one finding in the "huge win for something small" class, and it is B1.

## 4. Findings in detail

### A1 — `CONFIG_LWIP_MAX_SOCKETS` is silently 10. The board cannot serve 10 nodes.

**Where:** `sdkconfig.defaults` line 43; effective value in
`.pio/build/esp32dev/config/sdkconfig.h:513`.

`sdkconfig.defaults` says:

```
# Sockets: 1 listener + 6 nodes + 1 busy line + spares (lwIP ceiling is 16)
CONFIG_LWIP_MAX_SOCKETS=24
```

The comment knows the ceiling is 16 and the value asks for 24. In IDF 5.3.1,
`components/lwip/Kconfig` line 136:

```
    config LWIP_MAX_SOCKETS
        int "Max number of open sockets"
        range 1 16
        default 10
```

An out-of-range value in a defaults file is **discarded, not clamped**, so the
build takes the default. `sdkconfig.h` confirms:
`#define CONFIG_LWIP_MAX_SOCKETS 10`. `lwipopts.h:124` makes
`MEMP_NUM_NETCONN` the same number, and `sockets.c:260` is
`static struct lwip_sock sockets[NUM_SOCKETS]` — measured at 200 bytes in the
ELF, i.e. 20 bytes per socket.

**Socket accounting, measured against the source:**

| Consumer | Sockets | Evidence |
|---|---:|---|
| BBS listener | 1 | `src/core/bbs.cpp:149` |
| Caller sessions (10 nodes + busy + sysop) | up to 12 | `Bbs::nodes_[10]` + 2 |
| mDNS | 1 | one dual-stack socket, `mdns_networking_socket.c:463` |
| SNTP | 1 | `src/main.cpp:180` |
| announce (while posting) | 1 | `src/plugins/announce.cpp:439` |
| backup window (while open) | 2 | `src/core/backup.cpp:102` + accepted client |

With 10 sockets, the three always-on services take 3 and **seven callers fill
the board.** The 8th connection fails at `accept()`. The board advertises ten
nodes and reports ten in WHO, NODES and to the directory.

**This is almost certainly why the node count looked affordable.** The RAM was
found for ten nodes; the sockets never were.

**The fix costs 120 bytes of static DRAM** (6 × 20) plus heap for the extra
netconns — `lwipopts.h` sets `MEMP_MEM_MALLOC 1` and `MEM_LIBC_MALLOC 1`, so
lwIP's PCBs and netconns come from the heap, not from `.bss`.

**But 16 is not enough either.** Worst case above is 1 + 12 + 1 + 1 + 1 + 2 =
18. Steady state with the backup window shut is 1 + 12 + 1 + 1 = 15, leaving
one for announce — which means while the board is full, the directory heartbeat
takes the last socket and the backup window cannot be opened at all.

**Recommendation:** set 16, and size the node count from it. 16 − 3 always-on −
1 announce − 2 backup = 10 sockets for sessions, which is **8 caller nodes plus
the busy line and the sysop node**. If ten caller nodes are wanted, something
has to give: mDNS (1), announce polling only when a socket is free, or refusing
to open the backup window while the board is full. That last one is probably
right anyway.

**How you would know it went wrong:** the board stops accepting callers at a
fixed number below its node count, with `errno` 23 (`ENFILE`) at `accept()`.
Worth logging explicitly — today a failed `accept()` looks like nothing.

### B1 — `BackupService` is 12,192 bytes of permanently resident DRAM for a feature that is off

**Where:** `Bbs::backup_`, measured at offset 4, size 12,192, inside the
81,436-byte `Bbs` singleton (`_ZZN3Bbs8instanceEvE3bbs`, the largest symbol in
DRAM by a factor of fifteen).

Measured layout:

| Member | bytes |
|---|---:|
| `hdr_[1536]` HTTP request header | 1,536 |
| `out_[1024]` response buffer | 1,024 |
| `ziparc::ZipExport exp_` (`list_[66]` 3,168 + `manifest_[1536]` + `line_[176]` + `hdr_[96]`) | 5,016 |
| `ziparc::ZipImport imp_` (`items_[64]` 3,584 + `zipPath_[96]` + `ImportReport` 180) | 3,872 |
| `summary_[128]`, `detail_[112]`, `notes_[6]` 438, scalars | 744 |
| **total** | **12,192** |

This is 8.3% of the entire static DRAM budget and 35% of the remaining
headroom. It is resident from boot to reboot for a feature that requires the
BOOT button to be held **and** a sysop to be logged in, and then runs for
`backup_window_minutes` (default 5).

Related statics, same feature, same always-resident cost:

| Symbol | bytes | Purpose |
|---|---:|---|
| `users::validateFile::seen` | 5,250 | duplicate-handle check during upload validation |
| `users::validateFile::u` | 456 | scratch `UserRec` |
| `ziparc::ZipImport::open::tail` | 1,046 | zip central-directory tail |
| `ziparc::ZipImport::extract::probe` / `::cfgProbe` | 616 | 2 × 308 |

`users::validateFile` is called from exactly one place —
`src/core/ziparc.cpp:696`, the upload path. Verified by grep across `src/`.

**Total resident cost of the backup window: 19,560 bytes, 13.4% of static
DRAM.**

**What to do.** Allocate `BackupService` (and let it own the validation
scratch) when the window opens; free it when it closes. This is not "use the
heap" as an architecture change — `CLAUDE.md` already records the exception
("temporary inflate buffers during a backup upload"), and this is the same
feature, the same lifetime, and outside the caller loop in the same way.
Nothing in the BBS tick path changes.

**What it gives up.** If the allocation fails, the backup window does not open
and the sysop gets a message instead of a port. That is a real behaviour change
and it should be worded for a sysop, not a programmer: "not enough memory right
now — try with fewer callers on". The allocation needs ~12 KB contiguous; the
last on-board measurement (0.8.0, `CHANGELOG.md:215`) was 110,592 largest free
block at 107 KB static, and static has since grown ~39 KB, so a rough estimate
is ~71 KB largest block today. **That is an estimate, not a measurement** — it
should be confirmed on the board with
`heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)` before this is relied on,
and `MEM` already has somewhere to put the number.

**How you would know it went wrong:** the backup window refuses to open on a
busy board. Log the requested size and the largest free block at the point of
failure, so the message distinguishes "fragmented" from "genuinely full".

**Cheaper variant if the heap is not wanted at all:** B3 alone. `exp_` and
`imp_` are mutually exclusive — `BackupService::St` is a single enum
(`Idle, Headers, Body, Extract, Approve, SendZip, Reply, Linger`) and one
client is served at a time, so a request is a download or an upload and never
both. A union saves 3,872 bytes with no heap, no behaviour change, and an
invariant the state machine already enforces. Low risk; worth doing even if B1
is taken later.

### B2 — `seen[250][21]` is 5,250 bytes to detect duplicate handles

**Where:** `src/core/users.cpp:502`.

```c
static UserRec u;
static char seen[BBS_MAX_USERS][BBS_USER_MAX + 1];
```

It exists so that an uploaded `users.txt` can be checked for duplicate handles.
Storing a 32-bit hash of each handle instead is 1,000 bytes, saving 4,250. A
hash match is not proof, so on a match the check re-reads the file to confirm
before rejecting — which happens only when there really is a duplicate or a
1-in-4-billion collision, during an upload, once.

**What it gives up:** upload validation gets marginally slower in the case
where it is about to reject the file anyway.

If B1 is taken, this buffer should simply live in the same on-demand arena and
the saving is counted there instead — do not count B1 and B2 twice.

### C1 — full newlib printf/scanf is linked; the ROM has the small one

**Where:** `sdkconfig.esp32dev:1555`, `# CONFIG_NEWLIB_NANO_FORMAT is not set`,
against `sdkconfig.esp32dev:333`, `CONFIG_ESP_ROM_HAS_NEWLIB_NANO_FORMAT=y`.
The ESP32 ROM has the nano formatting functions; the build is not using them.

Measured from the map, per object:

| Object | bytes | Pulled in by |
|---|---:|---|
| `libc_a-vfprintf.o` | 14,080 | `fprintf` |
| `libc_a-svfprintf.o` | 13,729 | `snprintf` |
| `libc_a-svfiprintf.o` | 10,458 | `sniprintf` (IDF) |
| `libc_a-vfiprintf.o` | 10,092 | `iprintf` (IDF) |
| `libc_a-vfscanf.o` | 9,962 | `fscanf` — `src/plugins/example.cpp:68` |
| `libc_a-svfscanf.o` | 9,771 | `sscanf` — `backup.cpp:317`, `serialbridge.cpp:301` |
| `libc_a-svfiscanf.o` | 8,479 | `siscanf` (IDF) |
| **printf/scanf subtotal** | **76,571** | |
| `strtod` / `dtoa` / `mprec` / `gdtoa-*` | 12,288 | float conversion for the above |
| **total** | **88,859** | 83% of `libc.a`, 8.2% of the image |

The "pulled in by" column is from the map's archive-inclusion section
(`unleashed-bbs.map:1377–1389`), which names the referencing object for each.

Espressif's own guidance for this option: *"The exact difference in binary size
depends on which features the firmware uses, but 25 KB ~ 50 KB is typical."*
It also reduces stack usage in every function that calls `printf`, which is a
second-order benefit for `BBS_TASK_STACK`.

**What it gives up:** nano formatting does not support 64-bit integer formats
(`%lld`) or C99 features such as positional arguments. The board's own code
uses neither — a strict scan of format strings across `src/` found only `%a %d
%b %H:%M` style `strftime` patterns and one `"%u%% free"`. `strftime` is a
separate implementation and is unaffected.

The honest residual risk is the IDF's own logging: `CONFIG_LOG_DEFAULT_LEVEL=3`
(INFO) keeps IDF log lines compiled in, and any IDF component that logs a
64-bit value with `%lld` would print it wrongly. That is console output the
sysop sees, never anything a caller sees. Espressif ship this option and
default it on for the ESP32-C2, so it is a supported configuration.

**How you would know it went wrong:** garbled numbers in boot log lines. Worth
reading one full boot log after the change rather than assuming.

**C5 is the subset that has no caveat at all:** three call sites
(`backup.cpp:317`, `serialbridge.cpp:301`, `example.cpp:68`) pull in 19,733
bytes of scanf machinery. `backup.cpp` parses `"%7s %63s"` out of an HTTP
request line and `serialbridge.cpp` parses `"%11s %7s"`; both are two-token
splits that `strtoul` and a pointer would do. `example.cpp` reads a single
`%u` from a file. If C1 is taken these come from ROM anyway and C5 is moot; if
C1 is judged too risky, C5 is 19.7 KB with no behavioural cost whatsoever.

### C2 — every mbedTLS elliptic curve is compiled in; the board does no TLS

**Where:** `sdkconfig.esp32dev:1509–1520`, twelve
`CONFIG_MBEDTLS_ECP_DP_*_ENABLED=y` lines.

Measured, per object within `libmbedcrypto.a` (97,111 bytes of flash total):

| Object | bytes |
|---|---:|
| `ecp_curves.c.o` | **34,638** |
| `ecp.c.o` | 6,386 |
| `rsa.c.o` | 5,456 |
| `aria.c.o` | 3,404 |
| `sha3.c.o` | 1,928 |

`ecp_curves.c.o` alone is 3.2% of the whole image. The fixed-point tables are
visible individually in the ELF: `secp192k1_T`, `secp192r1_T`, `secp224k1_T`,
`secp224r1_T`, `secp256k1_T`, `secp256r1_T` at 384 bytes each, `secp384r1_T`,
`secp521r1_T`, `brainpoolP384r1_T`, `brainpoolP512r1_T` at 768 each,
`brainpoolP256r1_T` at 384 — 5,760 bytes of tables plus the curve parameters
and per-curve code around them.

Nothing in the firmware uses TLS. Verified by grep: no `esp_tls`, no
`mbedtls_*`, no HTTPS. ANNOUNCE is plain HTTP by design and the backup window
is plain HTTP. mbedTLS is present solely because
`CONFIG_ESP_WIFI_MBEDTLS_CRYPTO=y`, which the IDF Kconfig
(`components/esp_wifi/Kconfig:487`) shows selects exactly:

```
            select MBEDTLS_AES_C
            select MBEDTLS_ECP_C
            select MBEDTLS_ECDH_C
            select MBEDTLS_ECDSA_C
            select MBEDTLS_CMAC_C
            select MBEDTLS_ECP_DP_SECP256R1_ENABLED
```

**One curve.** The other eleven are mbedTLS's own `default y` and nothing on
this board asks for them. WPA3-SAE uses group 19, which is secp256r1.

**What it gives up:** if TLS is ever added — an HTTPS announce endpoint, an OTA
pull over TLS — a server presenting a certificate on a curve other than P-256
would fail to negotiate. In practice P-256 is what public TLS uses, but this
is a real constraint and it should be written down next to the setting rather
than discovered later.

`aria.c.o` (3,404) and `sha3.c.o` (1,928) are a cipher and a hash that nothing
on this board or in Wi-Fi uses, and are separate Kconfig switches.

### C3 / C4 — WPA2-Enterprise and IPv6

`CONFIG_ESP_WIFI_ENTERPRISE_SUPPORT=y`. The IDF's own help text
(`components/esp_wifi/Kconfig:723`) is blunt: *"disabling this will reduce
binary size"*. It is what pulls the X.509/PEM/TLS half of mbedTLS in alongside
the crypto half. `libwpa_supplicant.a` is 55,495 bytes measured; the
enterprise-specific part of that plus the mbedTLS X.509 path is **estimated**
at 10–20 KB. I could not measure it without a rebuild, and I did not rebuild.
**What it gives up:** the board can never join a WPA2-Enterprise network.
For a home BBS on a domestic AP that is free; if Improv provisioning is meant
to let anyone put this on any network, a university or corporate network would
be out.

`CONFIG_LWIP_IPV6=y`. Measured IPv6 objects in `liblwip.a`: `nd6.c.obj` 8,546,
`ip6.c.obj` 3,347, `mld6.c.obj` 1,520, plus smaller ones — **estimated** 13–15
KB of flash and roughly 1 KB of DRAM (`destination_cache` 480 bytes, the ND6
neighbour cache, and part of `dns_table`'s 1,184). **What it gives up: no IPv6
callers.** Note it does *not* free a socket — mDNS opens one dual-stack socket
either way (`mdns_networking_socket.c:463`).

`CONFIG_LWIP_DHCPS=y` (2,815 bytes) and the AP-side WPA objects `wpa_auth.c`
6,483, `wpa_auth_ie.c` 1,798, `esp_hostap.c` 875, `pmksa_cache_auth.c` 825
exist for SoftAP, which this board never runs. **Estimated** ~12 KB. The cost
is that a future "can't reach the network, fall back to an AP so you can
configure me" story becomes unavailable — which is worth weighing against
Improv, since Improv Serial does not need SoftAP but a browser-based fallback
might.

### D1 / D2 — `UserRec` is instantiated 29 times in DRAM

Seventeen function-local `static UserRec` scratch buffers, 456 bytes each,
**7,752 bytes**, all visible in `nm` as 456-byte symbols:

- `users.cpp` (6): `update::probe`, `range::u`, `count::u`, `add::probe`,
  `validateFile::u`, `(anon)::rewrite::u`
- `bbs_users.cpp` (7): `ulDrawRow::u`, `rowUsers::u`, `formSave::cur`,
  `formSave::cur_0`, `formSave::cur_1`, `cmdInfo::u`, `markAccount::u`
- `bbs.cpp` (4): `onPassword::fresh`, `saveCallStats::u`,
  `dayMinutesUsed::u`, `cmdPassword::probe`

Plus `Session::edit`, one per session: 12 × 456 = 5,472.

**Total `UserRec` footprint in DRAM: 13,224 bytes, 9% of the budget.**

Two consequences:

**D2 is the leveraged one.** Every byte removed from `UserRec` saves 29 bytes
of DRAM. `email[65]`, `address[65]` and `phone[21]` are 151 bytes — 4,379 bytes
of DRAM — for fields a telnet BBS arguably does not need to hold in RAM at all,
since nothing but the profile form and `USER EDIT` ever reads them and both
could read them from the file on demand. That is a product decision, not a
compiler one, and it is the single largest structural saving available that
does not touch the backup window.

**D1 is the risky one.** Three of those seventeen (`formSave::cur`, `cur_0`,
`cur_1`) are in one function, which tells you the compiler found three separate
`static UserRec` declarations in different scopes of `formSave`. A shared pool
of four slots with an RAII handle would recover ~5,900 bytes. **What it gives
up:** nothing a caller sees — but a slot-discipline error writes one caller's
record over another's, and account corruption is the worst failure mode this
board has. Not recommended ahead of B1 and D2; it is more risk for less money.

**D3:** `bbs_sysop.cpp` holds `g_cfgWas` 1,536, `g_cfgBuf` 1,536, `g_cfgSum`
448 and `g_cfgKeys` 384 — **3,904 bytes** resident for the `CONFIG` editor,
which already enforces one session at a time with a static guard. Same shape as
B1 and the same remedy.

### E1 — `BBS_TL_BYTES`: the arithmetic, and why not to

12 × 3,072 = 36,864 bytes, 25% of static DRAM and 61% of a `Session`
(`Timeline` is 3,484 of 5,716). It is the largest single lever on the board and
it should be left alone. The comment at `config.h:104` records why it is 3,072,
and `BBS_RX_ROOM` is 1,700 because a full form redraw is ~1.4 KB. Cutting to
2,560 saves 6,144 bytes and cuts the slack above `BBS_RX_ROOM` from 1,372 bytes
to 860 — which is the exact case that already bit once, a C64 caller typing
ahead through a PETSCII form redraw losing output.

Listed here only so the next person does not rediscover it and think it looks
free. It is the biggest number on the page and the worst thing to touch.

`BBS_TL_FRAMES` 96 (384 bytes/session, 4,608 total) is a softer target: 64
frames saves 1,536 bytes. **What it gives up:** fewer distinct timed output
frames in flight, so an effect with many short steps coarsens. Small money,
and it would need the fx code read properly before anyone acted on it, which I
have not done.

## 5. The brief's open questions, answered

**Wi-Fi driver buffers — do they hold something large?** Yes, but on the wrong
budget. `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=10` (≈16 KB),
`DYNAMIC_RX_BUFFER_NUM=32`, `DYNAMIC_TX_BUFFER_NUM=32`, `RX_BA_WIN=6`,
`MGMT_SBUF_NUM=32`. **These are allocated from the heap at `esp_wifi_init()`,
not placed in `.bss`** — "static" there means "fixed count, never freed". Total
measured Wi-Fi contribution to `.data`+`.bss` is small: `libpp.a` 3,339,
`libnet80211.a` 1,655, `libesp_wifi.a` 527, `libphy.a` 4,253. Cutting the
buffer counts frees heap, which is genuinely useful for B1's allocation, but
moves the static ceiling not at all. **Honest throughput cost:** fewer RX
buffers means dropped frames under burst and TCP retransmits. This board sends
a few hundred bytes at a time and would not notice — with one exception, the
400 KB backup zip upload, which is the only time it moves real data and is
exactly when B1 also wants heap. Tune these *and* B1 together or neither.

**lwIP sizing.** See A1, which is the finding. Beyond it:
`CONFIG_LWIP_TCP_SND_BUF_DEFAULT=5760` and `TCP_WND_DEFAULT=5760` are 4 × MSS
per connection, heap-allocated on demand; halving them halves per-connection
heap for a board whose largest single write is a screen. `MEMP_MEM_MALLOC 1`
means none of lwIP's pools are static, so there is nothing here for the DRAM
ceiling.

**FreeRTOS task stacks.** Also heap, not static — `xTaskCreate` allocates from
the heap. The one exception is `port_IntStack`, **3,072 bytes of `.dram0.data`**
(2 cores × `CONFIG_FREERTOS_ISR_STACKSIZE` 1,536), which is real static DRAM
and is the third-largest single DRAM symbol on the board. Stacks in this build:
`BBS_TASK_STACK` 8192, mDNS 4096, main 4096, esp_timer 3584, lwIP TCP/IP 3072,
event 2304, timer service 2048, idle 1536 × 2. **`uxTaskGetStackHighWaterMark`
is the way to size these and it needs a running board, so this report does not
guess at them.** Worth adding to `SYS` alongside the existing scheduler timing —
it is the one instrument missing from a board that already reports everything
else about itself, and the files plugin's stack arrays (`char cur[160],
tmp[176]` at `files.cpp:235`, `char full[192]` at 514) are new enough that
nobody has seen a high-water mark with them in the path.

**`const` tables in DRAM — the Xtensa trap.** Checked, and clean. Every command
and settings table is in flash: `_ZZN3Bbs12coreCommandsERhE1k` at `0x3f418aa4`,
the three `kSettings` tables at `0x3f419e34`, `0x3f4198f0`, `0x3f419f60` —
all `0x3F4xxxxx`, which is drom. The `const char* const[]` problem does not
bite here. Nothing needs doing; recorded so the next report does not re-check it.

**Struct padding.** Checked with `ptype /o`. `Session` has 32 bytes of holes
across sixteen gaps; over twelve sessions that is 384 bytes total. `UserRec` has
one 2-byte hole. **Reordering members is not worth doing** — it would churn a
struct that everything touches, for a quarter of one node's worth of savings,
and `ptype /o` will show the same holes to whoever looks next.

**The newly added subsystems.** SD/FATFS/SPI cost almost nothing in static
DRAM: `libfatfs.a` 60 bytes, `libesp_driver_spi.a` 145, `libvfs.a` 232,
`sd.cpp.o` 261. The `xmodem` engine holds **zero** static DRAM — its buffers
are per-instance members (`hdr_[3]`, `chkOut_[2]`, `chkIn_[2]`). `files.cpp.o`
holds 698. Their cost is flash — `libfatfs.a` 17,614, `libsdmmc.a` 15,745,
`libesp_driver_spi.a` 13,638, about 47 KB together — and heap at mount
(`CONFIG_FATFS_PER_FILE_CACHE=n` is already doing its job). **These were the
suspects and they are innocent.** If SD ever needs to come out, it is a build
profile for flash, not a RAM decision.

## 6. What is growing, and how fast

From `CLAUDE.md`'s own per-milestone records (Rob's figures; image sizes there
are decimal KB, bytes ÷ 1000, which is why 1001 KB reads as 63.7% of 1,572,864):

| Version | Image | Static RAM | Static as % of 180,736 |
|---|---:|---:|---:|
| 0.5.0 | ~900,000 | ~81,000 | 45% |
| 0.6.0 | 919,000 | 104,000 | 58% |
| 0.8.0 | 928,000 | 107,000 | 59% |
| 0.10.0 | 966,000 | 109,000 | 60% |
| 0.11.0 | 987,000 | 111,000 | 61% |
| 0.13.0 | 999,000 | 114,000 | 63% |
| 0.15.0 | 1,001,914 | 117,000 | 65% |
| **0.17.2** | **1,081,256** | **146,376** | **81%** |

**Static RAM grew 29,376 bytes in two milestones — more than the previous ten
milestones put together.** Decomposed:

- Node count 6 → 10, i.e. 8 sessions → 12: 4 × 5,716 = **+22,864 (78%)**
- `Session` itself 5,596 → 5,716 (raw input, SD screen flag): 120 × 12 = +1,440
- SD, files, xmodem, plugin DRAM: ~+1,200
- remainder ~+3,900, unattributed to a single cause

That is a reassuring decomposition: **the new subsystems were cheap and the node
count was not.** The line to watch is not "what did we add" but "how many
sessions are there", because at 5,716 bytes each with a hard 180,736 ceiling,
the node count is the only number on the board with that kind of leverage.

The figure to track next milestone is **`_bss_end − 0x3FFB0000`**, not
PlatformIO's percentage. At the current rate a third of the remaining headroom
goes per milestone.
