# Sat types: what each would take (2026-09-27)

A feasibility note for Rob, from the link lane at `1.2.0-link.10`. No code.
Words as settled today: a **sat**, **sats**; an **orbiter** feeds the board
data (camera, GPIO, sensors, Home Assistant); a **door sat** is one a caller
goes into, with `UPLINK`. The link itself is LINK.md; figures below are from it unless a
source is named.

## The answer first

| Type | Link work | Family | Board flash / RAM | Sat hardware | Work | When |
|---|---|---|---|---|---|---|
| Relay, one hop | a path per peer and a 2-byte wrapper in the engine; the relay forwards sealed frames it cannot open | none new for the data; the relay pairs as an ordinary peer (new kind) | about 3 KB flash; 0 static, about 60 bytes of heap | any ESP32; an external antenna model (WROOM-32U) where it matters | about 1.5 weeks with bench | after 1.2.0, and only if the LR test below does not cover the cases |
| Relay, multi-hop mesh | routing or flooding, loop control, path repair, all on one channel | a routed wrapper | 6-10 KB flash, 1-2 KB heap | 3 or more relays to test | 3-5 weeks, most of it bench | not planned |
| Remote control (GPIO) orbiter | none: ordinary sessions, one frame a message | **new core family: POINTS (id 3)**, shared by every data orbiter | the POINTS side 3-4 KB on top of the GPIO plugin; the point table on the heap | any ESP32, relay modules, the usual sensors | about 1 week, after the GPIO plugin | after the GPIO plugin (1.3.0 or later) |
| Home Assistant orbiter | none: same as GPIO | POINTS, the same family | **nothing beyond GPIO's**: HA, TLS and the token live on the sat | any ESP32 on the home Wi-Fi (WROOM is enough) | about 1 week after POINTS | after the GPIO orbiter |
| Custom sat | none: the protocol is documented | POINTS for data (stock firmware works), or a plugin family 128-239 with a plugin built in | 0 for a POINTS orbiter | anything that can run the link, or speak it over serial | 2 weeks for the template repo and a Python reference implementation | template with the GPIO orbiter; Python reference early, as a test |

**Recommendation.** Nothing in 1.2.0: it is closed and the bench still owes
it multi-board. After it, in this order:

- **An LR bench test** (1 to 2 days, no new protocol). It decides whether a
  relay is needed at all.
- **The POINTS family and the GPIO plugin together**, because the point
  table is the one thing every orbiter except the camera feeds.
- **The GPIO orbiter**, then **the Home Assistant orbiter** on the same
  family.
- **The sat template and a Python reference implementation** of the link,
  which is also the "somebody else's implementation" test this project
  keeps needing (lrzsz found an XMODEM bug our own client agreed with).
- **The one-hop relay**, if the LR test says so. A mesh, not unless a real
  board needs it.

## 1. Relay sat

Rob thinks it is easy. For one hop, with the relay only forwarding, it is
close to easy. The cost is in three places that are not the forwarding.

### One hop, specified

```
  board B  <--- ch C --->  relay R  <--- ch C --->  far sat F
  (on the router,          (no AP)                  (no AP)
   channel C)
```

- **One channel at both ends.** B is a station on the router and "must be
  the same as that of the connected AP" (LINK.md, Channels). R has one
  radio, so it talks to F on channel C too. Hopping R between two channels
  would cost every frame a channel switch and the far side's timing, for no
  gain: F follows the host's channel anyway. So a relay does not get round
  a channel change; it gets round distance and walls.
- **Keys: end to end, and the relay sees nothing.** F pairs with B through
  R. The pairing frames are the clear ones already (`PAIR_HELLO`, `OFFER`,
  `NONCE`, `REVEAL`); R forwards them. The ECDH secret, so `k_link` and
  every session key, is B's and F's alone. The 4-digit code the sysop
  compares at pairing is what rules out R sitting in the middle of the key
  exchange: a relay that swaps public keys makes the two codes differ
  (LINK.md, Pairing, "two codes match by chance once in 10,000").
  After that every data frame is AES-CCM with the 20-byte header as
  associated data, so **R can drop or delay frames and can do nothing
  else**: not read them, not alter them, not replay them (the `pn` window).
  R pairs with B as well, under its own key, for its own status and for
  "these are the sats behind me"; that key covers only R's own messages.
- **The wrapper, and the one real protocol change.** The engine knows a
  peer by the MAC a frame came from, and a relayed frame arrives from R's
  MAC. The header cannot say "originally from F": it is authenticated, so R
  cannot write into it. So R wraps: 1 byte "relayed" and 1 byte F's index
  in R's table, then the frame unchanged. A full frame is 250 bytes, the
  ESP-NOW limit on IDF 5.3.1, so a relayed peer's payload is **220, not
  222**: the engine's `kPayloadMax` becomes per peer. About 1% of
  throughput.
- **Paths are learnt, not configured.** B keeps, per peer, the next hop it
  last heard an authenticated frame through (direct, or R) and answers
  that way. A far sat that is sometimes in range of B directly sends
  through both; the duplicate has the same `pn` and the replay window
  drops it at no cost. The path moves to whichever works, with nothing for
  the sysop to set.
- **Discovery.** F's `DISCOVER` on channel C reaches R, which forwards it;
  B's `BEACON` comes back through R. The channel sweep is unchanged.
- **Latency.** An ESP-NOW frame is well under a millisecond on the air at
  24 Mbps. The relay's cost is its receive callback to its forwarding task
  and out again: a few milliseconds a hop, estimate, to measure. The
  engine's timers (20 ms to ACK, 150 ms first retry) have room for it. A
  keystroke through a door sat behind a relay would not be noticed.
- **Throughput.** Both hops share one channel, so every byte is on the
  air twice, and R cannot send while F does. Expect at best half of the
  direct figure, and the direct figure today is bound by the loop and the
  window, not the air (54 KB/s on the WROOM, 72-88 KB/s on the S3,
  LINK.md). Estimate 30-45 KB/s relayed at 24 Mbps: an XGA picture of
  90 KB in 2-3 s. At the 1 Mbps fallback on both hops (49 KB/s direct,
  bench), about 20-25 KB/s. Doors are keystrokes and screens: no issue.
- **What the board carries.** The path table (7 bytes a peer, 8 peers) on
  the engine's heap, the wrapper in the receive path, a relay kind, and
  LINK showing "via garden-relay". About 3 KB of flash. The relay's own
  firmware is small: pairing, a MAC table of the sats behind it, a ring,
  no reassembly, no crypto beyond its own session with B. A new repository
  (the camsat layout), most of its code the link core and camsat's radio.
- **Host testing needs one new thing**: the host radio is UDP where
  everybody hears everybody. It needs a reach table ("F cannot hear B") so
  a test can prove the relayed path is the only one.

### A real multi-hop mesh

What one hop does not need and a mesh does:

- **Routing.** Either a routing protocol (next hop per destination,
  sequence numbers so stale routes lose, AODV or Babel in shape), or
  flooding: every relay rebroadcasts with a hop count (TTL) and drops what
  it has seen. Espressif's own `esp-now` component does the second: its
  frame header carries `forward_ttl` ("number of hops in data transfer")
  and `forward_rssi` ("will not be transferred, in order to avoid network
  congestion"), Apache-2.0
  ([espnow.h](https://github.com/espressif/esp-now/blob/master/src/espnow/include/espnow.h)).
  Flooding is cheap to build and costs airtime on every frame; bulk
  pictures flooded through three relays is three times the air for one
  picture.
- **Loops.** A TTL and a duplicate cache per relay (source, `pn`) prevent
  them. With routing, split horizon or sequence numbers do.
- **Channels.** Still one, the router's, for every node. Airtime is shared
  by every hop in radio range of each other, so throughput falls roughly
  with the hop count.
- **Repair.** A relay that dies leaves the sats behind it dark until a new
  path is found. Our end-to-end retries (150 ms doubling to 1.2 s, 8 tries)
  compound over several lossy hops; a mesh wants per-hop retries under the
  end-to-end ones.
- **Trust.** Routing messages from relays must be authenticated (each
  relay's own key with B), or anybody in range can poison routes. Since
  every path ends at B, the simplest sound design is **B computes the
  routes** from what each relay reports hearing, and puts them in the
  wrapper (source routing). A tree rooted at the board, not a general mesh.
- **Not ESP-WIFI-MESH.** It is built on Wi-Fi AP and station links with
  the root joined to the router, which would make the board a mesh root:
  a different network stack under the BBS, and far more flash than the
  link.
- Estimate: 3 to 5 weeks, most of it on a bench with three or more relays
  and walls, before it could be called reliable.

### Does LR mode or an antenna make the mesh unnecessary?

Very likely for the cases a hobbyist has (the garden, the barn, the end of
the drive), and it should be tried before a relay is built.

- **LR mode** is Espressif's own PHY: "the raw PHY data rate LR is 1/2 Mbps
  and 1/4 Mbps", "a one-kilometer line of sight range", "about 2 to 2.5
  times the distance of 11B", and 4 dB better sensitivity
  ([IDF 5.3.1 Wi-Fi guide](https://docs.espressif.com/projects/esp-idf/en/v5.3.1/esp32/api-guides/wifi.html)).
  ESP-NOW takes it per peer: `esp_now_set_peer_rate_config` with
  `WIFI_PHY_MODE_LR` and `WIFI_PHY_RATE_LORA_250K` or `_500K` (in IDF
  5.3.1's `esp_wifi_types_generic.h`), which is the call the satellite's
  rate fallback already makes.
- **The catch is the board.** B is a station on an ordinary router. The
  guide says a station in mixed mode (b/g/n plus LR) "is compatible with
  traditional 802.11 mode" and negotiates plain BGN with the router, so
  adding LR to B's protocol bitmap should not cost its Wi-Fi. **Whether B
  then receives LR ESP-NOW frames while associated is not in the guide and
  is the thing the bench test must show.** If it does, a far sat can run
  LR to the board with no relay at all. If it does not, LR still works
  sat to relay, with the relay talking to B at normal rates.
- **Throughput at LR 250K**: estimate 12-20 KB/s, so an XGA picture in 5-8
  s. Fine for a timelapse and for doors; it would feel slow for a caller's
  SNAPSHOT, and the spinner covers it.
- **Antennas.** The ESP32-WROOM-32U and the ESP32-CAM (after moving its
  0-ohm antenna resistor) take an external antenna. A directional antenna
  at the far sat alone adds its gain to the link budget both ways; every
  6 dB roughly doubles line-of-sight range. Legal limits are on radiated
  power, not range: the EU caps 2.4 GHz at 20 dBm EIRP, so a high-gain
  antenna there means turning the transmit power down, and the gain on
  receive is what is left. The US allows more for fixed point-to-point
  links. The docs should say "check your country's limit", not promise a
  distance.
- **What neither fixes: a building in the way.** 2.4 GHz does not bend
  round a house. That is the case a one-hop relay is for, and it is the
  only case worth building one for.

**The test (1 to 2 days):** B with LR added to its bitmap, still joined to
the router; the camsat satellite at LR 250K; measure whether the board
hears it, picture throughput, and distance against 11b at 1 Mbps, on the
bench boards and outdoors.

## 2. Remote control (GPIO) orbiter

Switches, relays and sensors on another ESP32, driven by the GPIO plugin's
point table (queued in CLAUDE.md: named points, a dashboard, standard
sensors, triggers).

- **The design point: the board's point table does not care where a point
  is.** A point is a pin on the board, or "pin 5 on sat `shed`", or later
  an HA entity (section 3). The dashboard, the screens, the triggers (a PIR
  firing SNAPSHOT) and the permissions work on points; only the driver
  differs.
- **A new core family, POINTS (id 3)**, used by every data orbiter:

  | Type | Dir | What |
  |---|---|---|
  | DECLARE | P to H | the points this sat offers: index, name (12), kind (input, output, analog, sensor), unit, range. At connect and when they change |
  | CONFIG | H to P | per point: pin, driver (DHT22, BME280, DS18B20, PIR, reed, relay), report interval, change threshold, the failsafe state. The board's CONFIG owns it, as camsat's settings |
  | VALUE | P to H | index, value (fixed point, 32 bits), timestamp; on change past the threshold and at the interval |
  | SET | H to P | index, value; reliable. Answered by VALUE |
  | EVENT | P to H | index, edge; for triggers (motion, a door contact) |

  Every message fits one frame, so no bulk window and no PSRAM. The link
  already gives order, retries, sessions and sealing.
- **Failsafe.** An output goes to its configured safe state when the link
  has been down N seconds, and at the sat's boot before the board has said
  anything. A relay left on because the board rebooted is the failure a
  sysop remembers.
- **Permissions.** SET needs the GPIO plugin's write level, staff by
  default. A public telnet board that switches mains relays should need
  the sysop to open each output to callers, point by point.
- **Board cost.** The POINTS side is 3-4 KB of flash (estimate) on top of
  the GPIO plugin, which is its own item. The point table goes on the heap
  at plugin start: static DRAM on the WROOM is 16 KB free, and 32 points
  at about 40 bytes is 1.3 KB that has no business being static.
  **Sensor drivers live on the sat**, not the board, so every driver moved
  to an orbiter is flash the WROOM does not spend.
- **Hardware.** Any ESP32 dev board; relay modules with a 3.3 V input;
  DHT22, AHT20, BME280, DS18B20, BH1750, a PIR, a reed switch. A battery
  sensor sat sleeps the way camsat does and wakes on its interval or an
  edge.
- **Work.** The GPIO plugin itself (point table, CONFIG, dashboard,
  triggers) is 1 to 2 weeks and is the prerequisite. The family, the sat
  firmware and the board side on top of it: about 1 week, plus half a day
  to a day per sensor driver.

## 3. Home Assistant orbiter

HA was dropped from the board in 0.17.1 for about 40 KB of flash and 9 KB
of static RAM (MQTT and TLS), on a WROOM that could not spare either. On a
sat that is all it does, the cost lands on a board with nothing else to
do, and the board pays nothing.

- **Same family as GPIO.** An HA entity is a point: a `sensor` is analog,
  a `binary_sensor` an input, a `switch` or `light` an output whose SET
  becomes a service call. The board cannot tell an HA orbiter from a GPIO
  one, and needs no HA code at all.
- **On the home Wi-Fi, beside the link.** The orbiter joins the router as
  a station, so its channel is the router's, which is the board's. ESP-NOW
  and Wi-Fi then run together exactly as they do on the board.
- **Talking to HA**, two ways, the sysop picks:
  - **WebSocket API**: authenticate with a long-lived access token
    (`{"type": "auth", "access_token": ...}`), `subscribe_events` for
    `state_changed` so values are pushed, not polled, `call_service` for
    outputs ([HA WebSocket API](https://developers.home-assistant.io/docs/api/websocket/)).
    No extra software on the HA side.
  - **MQTT**, for a sysop who already runs a broker: ESP-IDF's own
    `esp-mqtt` client, subscribe to the chosen state topics only.
  TLS is optional (HA on a LAN is commonly plain HTTP on 8123) and, when
  wanted, is the sat's mbedTLS and the sat's heap.
- **The token is the risk, and it never touches the board.** A long-lived
  HA token acts as its user. It must be a **dedicated HA user, not an
  admin**, and it is typed into the sat over its USB console, never into
  the board's CONFIG: that would send it across telnet in the clear and
  put it in `system.cfg` and every backup zip. The board sends the sat only
  the entity ids to feed (sealed, over the link). HA's WebSocket guide
  says nothing about what a non-admin user may do, so check that before
  promising a least-privilege setup.
- **Hardware.** Any ESP32 with Wi-Fi. A WROOM has plenty of heap for one
  TLS connection when it runs nothing else. It can be the GPIO orbiter too.
- **Work.** About 1 week once POINTS exists: the WebSocket client, entity
  mapping, the setup console. MQTT another 2 to 3 days.

## 4. Custom sat (a third party's)

- **A documented family.** Already there: LINK.md is the protocol
  (frames, pairing, sessions, families), plugin families are 128-239,
  assigned by a row in LINK.md's table, and 240-254 are anybody's for
  experiments.
- **The biggest enabler is POINTS, not an SDK.** A board runs the firmware
  the installer gave it; there is no loading plugins at run time. A custom
  sat with its own family needs a board built with its plugin (the
  external-plugin mechanism, `unleashed-plugin.ini`, works today, and camsat
  is the proof). A data orbiter that speaks POINTS works on **stock**
  firmware, and most third-party sats will be data.
- **An SDK: a template repository**, `unleashed_sat_template`: the link
  core fetched at a pinned commit (camsat's `fetch_core.py`), the generic
  half of camsat's firmware lifted out (the radio with the per-board rate
  table, pairing records in NVS for up to five boards, the pairing button
  and LED, the channel sweep), one example family, and a board-side
  plugin skeleton in the plugin-repository layout. About a week, most of it
  moving code camsat already has into a shape others can copy.
- **A Python reference implementation** of the link over the serial
  transport (frames, AES-CCM, P-256 ECDH, HKDF, with the `cryptography`
  package): about a week, and it earns its keep twice. A Raspberry Pi or a
  PC becomes a sat on a cable, and the board gains a test against an
  implementation that did not grow up beside it.
- **Pairing story: unchanged.** The same two physical acts: `LINK PAIR` on
  the board, the sat's button or boot window, the 4-digit code compared. A
  sat of an unknown kind shows as `device`. A sat whose family has no
  plugin on this board should be named in LINK ("no plugin for family
  140"), not paired silently into nothing. Kind ids want a registry beside
  the family table.
- **Licence.** The link core is GPL-3.0-or-later. A sat that links it is
  GPL if it is distributed. A closed sat is possible only by implementing
  the documented protocol itself, which the protocol allows. The template
  says so plainly.
- **Work.** About 2 weeks for the template and the Python reference
  together, best done beside the GPIO orbiter so the template's example is
  a real one.
