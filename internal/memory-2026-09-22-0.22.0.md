# Static RAM report: µnleashed BBS 0.22.0

Date: 2026-09-22 (evening)
Previous report: `internal/memory-2026-09-22.md` (0.21.1, this morning).
Tree: uncommitted 0.22.0 on top of `c1c225d` (0.21.9).

Nothing in the project was built, changed, committed or flashed. The 0.22.0
figures are from the existing `.pio/build/esp32dev/` artefacts (16:46). The
0.21.9 figures are from a throwaway build of `HEAD` in a detached worktree
under the session scratchpad, done so every delta below is a measured
difference between two ELFs rather than an estimate. That worktree has been
removed. PlatformIO reported 175,484 for it, which is the figure this report
was handed for 0.21.9, so the baseline is the real one.

---

## 0. The headline

**176,000 of 180,736 bytes. 4,736 free. 97.4% of the real ceiling.**
PlatformIO calls it 53.7%.

**0.22.0 cost 512 bytes of static DRAM and 26,784 bytes of flash.** Every
byte of both is accounted for below, symbol by symbol and object by object.

**Mail as a subsystem cost 12 bytes of static DRAM.** This morning's report
estimated 4 to 8 KB for it and said it did not fit. It fit because it reused
`Session::compose`, the mail index already in RAM, and the per-node arrays
chat already had: the entire cost is `g_inBox[12]`. Rob's framing works when
it is followed, and this is the clearest example yet. The price was paid on
the stack instead (three new frames of 864 to 912 bytes) and in flash
(+4.3 KB), both of which the board can afford.

**The trend across six measurements** (all `_bss_end - 0x3FFB0000`, the
0.21.3 and 0.21.5 figures from `CLAUDE.md`):

| build | static DRAM | headroom | what moved |
|---|---:|---:|---|
| 0.17.2 (09-20) | 146,376 | 34,360 | |
| 0.21.1 (09-22 am) | 175,960 | 4,776 | forums, composer, identity: +29,584 |
| 0.21.3 | 170,232 | 10,504 | `seen` and `g_cfgWas` hashed: −5,728 |
| 0.21.5 | 174,864 | 5,872 | `BBS_COMPOSE_MAX` 1152 → 1536: +4,632 |
| 0.21.9 | 175,488 | 5,248 | forums layout, chat markers: +624 |
| **0.22.0** | **176,000** | **4,736** | info plugin +466, `bellOff` +48 |

Two things that table says. First, **the only recovery in four days was the
cheap half of one recommendation** (the two hash conversions), and 81% of it
was spent again within one version. Second, **the rate has dropped**: 0.21.5
to 0.22.0 is +1,136 across three versions, against +29,584 in the one before
them. The team has learned the arithmetic. The board still has less headroom
than one caller's `compose` buffer.

**Nothing in the "saves a lot for almost nothing" category is new.** The
thing in that category is the same thing it was on 2026-09-20 and this
morning: `BackupService::exp_` and `imp_` as a union, 3,872 bytes, no heap,
no behaviour change, invariant already enforced by its own state machine.
It has now been recommended three times. Everything else worth having costs
either a code change with a guard or a caller-visible trade.

**One finding changes how the board behaves for callers** and is flagged
here rather than buried: `CONFIG_LWIP_IPV6=n` (1,393 bytes static, 13.8 KB
flash) takes the board off IPv6. Nothing in `src/` uses it, the mDNS
component builds without it, but a caller on an IPv6-only path loses the
board. Not recommended without Rob deciding that is fine.

### What that means against `BBS_TASK_STACK`

The BBS loop task has 8,192 bytes, allocated from the **heap** by
`xTaskCreatePinnedToCore` (`pvPortMallocStack` is `pvPortMalloc` in IDF
5.3.1), so it is not in the 180,736. Summing static frames along the
deepest plausible chains, plus ~800 for newlib's `vfprintf` at the bottom
of anything that writes a file:

| chain | frames | total |
|---|---|---:|
| backup upload: `tick` → `service` → `readClient` → `ZipImport::apply` → `extract` → `vfprintf` | 160+208+1,376+1,648+848+800 | ~5,040 |
| file approve: `tick` → `onKey` → `files::onKey` → `doApproveQuiet` → `setDesc` → `vfprintf` | 160+128+1,216+768+640+800 | ~3,710 |
| mail open: `tick` → `onKey` → `chat::onKey` → `mailOpen` → `mailRewrite` → `vfprintf` | 160+128+656+912+832+800 | ~3,490 |
| forum read: `tick` → `onKey` → `forums::onKey` → `showMessage` → `codes::row` → Term | 160+128+416+2,128+128+~100 | ~3,060 |

Those are static sums and omit interrupt frames, which on this board land
on `port_IntStack`, not the task stack. **The deepest chain has ~3 KB of
margin**, and it is the backup path, which existed before 0.22.0. The mail
chains added this version are shallower than the file-approve chain that
was already there.

The measurement that replaces all of this arithmetic already exists:
`SYS` prints `plat::stackFree()`, the high-water mark in bytes, since
0.21.3. **It has not been reported here.** One reading from Rob's board
after a mail session, a backup upload and a forum read settles both the
margin and finding #2 below. Ask for it.

## 6. Heap, briefly, because it is now part of the same story

This report is about static DRAM, but two facts collided while writing it:

- `sdkconfig.defaults` records that **a live board reached 19,736 bytes of
  minimum free heap and restarted on its own**, which is why the lwIP send
  buffers were cut to 2,880 and the Wi-Fi dynamic buffers to 16.
- `_heap_start` is `_bss_end`. Static growth eats heap one-for-one.

So a recommendation that moves 12 KB from `.bss` to "allocate when the
window opens" (#1b) makes 12 KB of static room and then **takes 12 KB of
heap when a sysop opens the backup window**, on a board that has been seen
at 19.7 KB free. That is a real trade and this morning's report did not say
it plainly. The union variant (#1) has no such trade, which is one more
reason it is the one to do.

Knobs that are heap, not static, and where the true saving lies if heap is
the next wall (all verified against
`components/esp_wifi/Kconfig` in the installed 5.3.1; the static RX buffers
are allocated by `wifi_malloc` → `heap_caps_malloc_prefer` in
`esp32/esp_adapter.c:74`, not placed in `.bss`):

| Kconfig | now | range | each | heap saved | honest cost |
|---|---:|---|---:|---:|---|
| `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM` | 10 | 2..25 | 1,600 | 10 → 6: **6,400** | frames the driver can hold before the stack drains them. Ten callers reading text is a few frames a second; a YMODEM-1K upload is one 1,029-byte block then a wait. Six is comfortable, four is the point to measure a transfer before trusting it |
| `CONFIG_ESP_WIFI_RX_BA_WIN` | 6 | 2..32 | small | little | AMPDU reorder window; lowering it caps aggregation throughput the board never approaches |
| `CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM` | 16 | 0..128 | on demand | already cut | |

Measure `MEM`'s "heap low since boot" before and after, with a YMODEM
transfer timed on the same card. If a 60 KB download takes the same wall
time at 6 as at 10, the buffers were never the bottleneck, which is the
expected result for a stop-and-wait protocol.

## 7. The recommendations

### 1. `BackupService::exp_` and `imp_` as a union: 3,872 bytes, for nothing

Carried from 2026-09-20 (B3) and this morning (#1). `Bbs::backup_` is still
12,192 bytes at offset 4 of the singleton, `exp_` (`ZipExport`, 5,016) and
`imp_` (`ZipImport`, 3,872) are still both resident, and `BackupService::St`
is still one enum that means a request is a download or an upload and never
both. **Third time recommended, unchanged, no reason found not to.** If the
next milestone report says this again, the finding is not the union.

With it, the rest of the backup family is still worth 16,118 on heap at
window open (`backup_` 12,192 + `seen` 1,000 + `validateFile::u` 492 +
`ziparc.cpp.o` 2,434), with the heap trade in §6 stated.

### 2. The 22 `static UserRec` scratch buffers: 10,824 bytes, and the evidence has improved

Carried from this morning (#2). Still 22 × 492, still `bbs.cpp` 4,
`bbs_sysop.cpp` 3, `bbs_users.cpp` 7, `users.cpp` 8. What changed is the
evidence:

- **`chat::mailSend` already puts a `UserRec` on the stack**, inside a
  1,232-byte frame, on the caller's path, in code that has been on the board
  since 0.17.11. The pattern the comments say is unsafe ("static: off the
  task stack") is in production in the plugin that uses accounts most.
- **`SYS` reports the high-water mark** (`plat::stackFree()`, 0.21.3). The
  number that decides this exists and nobody has quoted it.
- The deepest chain in §5 has about 3 KB of margin before any conversion,
  and the first tranche (the eight leaves in `users.cpp`, 3,936 bytes)
  nests at most one record deep.

**Do it after reading `SYS` once**, and put the reading in the CHANGELOG so
the next report can compare.

### 3. Form context and composer share storage: 11,856, re-checked against 0.22.0

The per-session exclusivity this morning's report established still holds,
with one new writer and one new reader of `compose`:

| touches `s.compose` | state | file |
|---|---|---|
| chat mail write | `SState::Plugin` | `chat.cpp:2475-2533` |
| forum post | `SState::Plugin` | `forums.cpp:1758-2322` |
| **info page edit** | `SState::Plugin` (`claims::Res::Info`) | `info.cpp:352-401` |
| **info page read at the prompt** | `SState::List` via `startPluginList` | `info.cpp:157-293` |

And still **no plugin touches `s.edit`, `s.fields` or `s.form`** (grep is
empty), and the three form entry points all set `SState::Form`. A form
cannot open during a list, and a plugin-owned caller is not in a form. So:

- `compose` 1,537 versus `edit` 492 + `fields` 320 + `form` 176 = 988.
  A union is 1,537, saving **988 × 12 = 11,856**. Unchanged.
- `pwA/pwB/pwC` (99) are also form-or-login only, and login is not
  plugin-owned either: another **1,188** on the same invariant.
- The pool-of-six variant, no invariant, a refusal message for the seventh
  simultaneous form: **5,928**.

The guard this morning's report asked for (an owner byte set on entry to
either subsystem, checked on entry to the other, refuse rather than reuse)
is now more necessary, not less: there are three writers, and one of them
(info) reads the buffer across list passes. The project's own history says
what happens to an invariant nobody wrote down.

### 4. Reorder `Session` and `UserRec`: about 600 bytes for nothing (new)

From the DWARF layout, `Session` has fourteen padding holes totalling 27
bytes, from `bool`s interleaved with `uint32_t`s: after `ip[16]` (1), after
`newAccount` (2), after `loggedIn` (1), after `idleWarned` (2), after
`rawInput` (1), after `watchSecs` (1), after `countdown` (3), after
`landing` (3), after `level` (1), after `histPos` (3), after `term` (3),
after `mb` (3), and two inside `Timeline` (3). Grouping the 4-byte members
together and the bytes together recovers roughly 24 per session,
**~288 across twelve**.

`UserRec` has 11 bytes of holes (after `profile` 2, `retired` 3, `pass` 1,
`calls` 2, tail 3). It is **not** an on-disk format (`users.txt` is text),
so reordering is safe, and it exists 34 times (22 statics + 12 `edit`):
**~340 bytes**.

`MailRec` and `CallRec` are on-disk formats with static asserts; leave them.

Zero risk, zero behaviour change, one commit. Small, but it is the only
entry on this list that costs literally nothing, and `bellOff` just showed
what a `bool` in the wrong place costs: 4 bytes ×12 for a 1-byte field.

### 5. `serialbridge::g_back` allocated at plugin start: 1,024 bytes (new)

`serialbridge.cpp:83` `char g_back[kScrollback]` is resident on every
board, and the plugin is off unless `[plugin:serial]` switches it on. Chat
already does the right thing for exactly this shape: `g_hist` is a
`calloc` in `start()` and a `free()` in `stop()` (`chat.cpp:2788, 2814`),
with a fallback to the default if the board cannot spare it. Same pattern,
same lifetime (plugin start, never in the loop), 1,024 bytes back on every
board that does not bridge a serial device. `g_back` is the whole of that
object's resident cost bar 30 bytes.

### 6. `announce`: 768 by aliasing, 504 by policy (new)

- `g_request[768]` and `g_reply[768]` are never live together:
  `Stage::Sending` writes from `g_request`, `Stage::Reading` fills
  `g_reply` from zero. Aliasing them saves **768**. The one ordering trap:
  `announce.cpp:479-480` clears `g_reply` at the *start* of an exchange,
  which under aliasing would clear the request just built; move that clear
  to the transition into `Reading`. Ten lines.
- `g_servers[4]` is 1,008 bytes for four directories at 252 each (`host[96]`
  + `path[96]` + `result[48]` + scalars). One directory exists. `kMaxServers`
  2 saves **504**; this is a policy question for Rob, not an engineering one.
- `g_body[512]` is formatted, then copied into `g_request` by `%s`.
  Formatting it in place at the tail of `g_request` saves **512** but
  changes what `ANNOUNCE TEST` points at; smaller and fiddlier than the
  other two.

### 7. `SubjRow` subject text: 3,328 (carried)

`g_subjRow` grew from 4,352 to 4,608 since this morning (a `first` field,
4 bytes per row, for the permanent subject number, which is the right
fix for "1 above, 4 below"). The 52-byte `subject[]` per row is still a
copy of what `INDEX.TXT` holds at a fixed stride, and the recommendation is
unchanged: keep the four counters and the hash, read the subject back when
the row is drawn.

### 8. CONFIG editor at open: 2,944 (carried, smaller)

`g_cfgBuf` 1,536 + `g_cfgSum` 448 + `g_cfgKeys` 384 + `g_subBuf` 512 +
`g_cfgWas` 64 (was 1,536; hashed in 0.21.3, credit where due). Same
argument, same heap-at-open trade as #1b, one-at-a-time editor.

### 9. `CONFIG_LWIP_IPV6=n`: 1,393 static, 13,770 flash text, and the board leaves IPv6

Now measured rather than estimated: `nd6.c.o` 940 (`destination_cache`
480, `neighbor_cache` 220, `prefix_list` 140, the rest), `sockets.c.o`
`socket_ipv6_multicast_memberships` 448, five bytes elsewhere. Flash:
13,770 of `.flash.text` in `nd6`, `ip6`, `mld6`, `icmp6`, `ethip6`,
`ip6_frag`, plus their rodata.

Checked before recommending: nothing in `src/` uses `AF_INET6` or an IPv6
address type; `components/lwip/Kconfig` has no `select LWIP_IPV6` from
anything this board builds; the mDNS component's socket layer carries 14
`CONFIG_LWIP_IPV6` guards, so it builds IPv4-only.

**Caller-visible**: the board stops answering on IPv6 entirely. On Rob's
LAN today that is almost certainly nothing. On the internet, once the board
is exposed, an IPv6-only caller (some mobile carriers) cannot reach it, and
the directory's `/64` anti-spam logic becomes moot for this board. Rob's
call.

### 10. `Timeline::fr_` 96 → 64: 1,536 (carried, last)

Unchanged argument. Behind everything above.

## 10. Reproducing this

```sh
TC=~/.platformio/packages/toolchain-xtensa-esp-elf@13.2.0+20240530/bin
GDB=~/.platformio/packages/tool-xtensa-esp-elf-gdb/bin/xtensa-esp32-elf-gdb.exe
ELF=.pio/build/esp32dev/firmware.elf

# the only RAM number that means anything: (_bss_end - 0x3FFB0000) vs 0x2C200
$TC/xtensa-esp32-elf-nm.exe $ELF | grep -E ' _bss_end$'

# every DRAM symbol, biggest first
$TC/xtensa-esp32-elf-nm.exe --size-sort -S --radix=d -C $ELF \
  | awk '$1+0 >= 1073414144 && $1+0 < 1073590144' | sort -k2 -rn | head -40

# struct layouts with padding holes
$GDB -batch -nx -ex "set pagination off" -ex "set max-value-size unlimited" \
     -ex "ptype /o struct Session" -ex "ptype /o Bbs" $ELF

# every function's static frame: the entry immediate is the frame size
$TC/xtensa-esp32-elf-objdump.exe -d -C --no-show-raw-insn $ELF \
  | grep -A1 -E '^[0-9a-f]+ <' | grep -B1 'entry' | grep -oE 'entry\s+a1,\s*\S+'

# a baseline for exact deltas: build HEAD in a detached worktree
git worktree add --detach /tmp/base HEAD
cp include/secrets.h sdkconfig.esp32dev dependencies.lock /tmp/base/ ; cp -r managed_components /tmp/base/
(cd /tmp/base && pio run -e esp32dev)      # 84 s here, then diff the two nm outputs
git worktree remove --force /tmp/base
```

Traps carried forward, plus one new:

1. `nm` marks flash `.rodata` as `d`/`D` too. Filter every RAM figure by
   address.
2. GNU ld attributes the whole merged string pool to the first object
   contributing `.rodata.str1.1`; this build says `backup.cpp.o` owns 124 KB
   of rodata. It does not.
3. **New**: `git worktree remove` fails on Windows with "Filename too long"
   when the worktree is under a deep temp path. `rm -rf` the directory, then
   `git worktree prune`.
