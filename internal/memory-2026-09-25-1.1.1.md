# Memory report: µnleashed BBS 1.1.1 (four boards)

Date: 2026-09-25
Tree measured: `v1.1.1-dev.1` (38fcca9), built in a detached scratch worktree
(`release-prep/wt-opt111`), all four developer environments, every generated
`sdkconfig.<env>` deleted before the first build.
Previous reports: `internal/optimize-2026-09-23-1.0.0.md` (1.0.0),
`internal/memory-2026-09-22-0.22.0.md`, `internal/memory-2026-09-22.md`.

Nothing in the main checkout was changed except this file. Nothing was
committed, flashed or deployed. Thirteen measurement-only variants were
built in the scratch worktree, each adding Kconfig lines (and for one of
them a three-line code edit) and reverted with `git checkout` straight
after; the worktree is clean at the tag and its four build directories
hold the unmodified baseline again.

Baselines for the trend, all measured off ELFs already on disk:
1.0.3 (`wt-1.0.2`, 9915d58), 1.1.0 (`wt-reg` e0f1b13 for esp32dev,
`wt-rel` b5127f4 release envs), 1.1.1-dev.0 (`wt-rel111` 801888a, release
envs). Release and developer environments differ only by `-DBBS_RELEASE`;
at 1.1.0 both esp32dev ELFs are 162,992, so the two are compared freely.

## 0. Bottom line

- **No board is over, and only the camera boards are tight.** Static DRAM
  free: ESP32-CAM 4,792, Freenove 6,248, WROOM 17,728, S3 92,048. The
  brief's 4,912 and 6,368 are 1.1.1-dev.0: dev.1's picture work cost 120
  bytes on each camera board (`g_job` +48, `g_sizeChoices` 48, the rest
  scalars).
- **Two things are in the "huge for small" category, both measured:**
  1. **Four Kconfig lines give back about 200 KB of flash on every image
     and 3.3 KB of static DRAM, and a caller sees none of it.** The
     ESP32-CAM goes 90.1% → 77.4% of its slot, the WROOM 82.1% → 69.8%.
     Newlib nano formatting alone is 69.5 KB on every board and also takes
     about 640 bytes off every formatted-output chain on every task stack.
  2. **On the two camera boards, `.bss` in PSRAM gives back 121,302 bytes
     of internal DRAM** (static free 4,792 → 126,112 on the ESP32-CAM, and
     the same bytes to the internal heap, which the bench saw at 9,159 with
     the camera up). The cost is real and is Rob's call: a camera image on
     a board whose PSRAM is missing or dead boot-loops instead of running
     as a plain BBS, and the session pool moves into cached PSRAM, which has
     to be measured against Rule no. 1 before it ships.
- **Caller-visible:** only item 2's latency question. Nothing else here
  changes what a caller sees. **Sysop-visible:** item 2's boot behaviour,
  silent assertions (a failed assert prints an address, not a line), and
  taking the lights plugin off the camera profiles.
- **A correction to the 1.0.0 report:** IPv6 is not caller-visible. Every
  socket the board opens is `AF_INET` and nothing ever gives the interface
  an IPv6 address, so `CONFIG_LWIP_IPV6=y` is dead weight: 26,240 bytes of
  flash and 1,784 of static DRAM, measured.
- **Quietly growing:** flash. The WROOM image grew 103 KB between 1.0.3 and
  1.1.0, and the ESP32-CAM grew 8.4 KB in one dev bump today. At the
  1.0 → 1.1 rate the ESP32-CAM's slot is full in about a minor version and
  a half. Item 1 buys roughly two minor versions back on every board.

- **ESP32 ceiling:** the generated `.pio/build/<env>/memory.ld` says
  `dram0_0_seg (RW) : org = 0x3FFB0000 + 0, len = 0x2c200 - 0` (180,736),
  and `iram0_0_seg (RX) : org = 0x40080000, len = 0x20000 + 0x0` (131,072).
  Used is `_bss_end - 0x3FFB0000` off each ELF; IRAM used is
  `_iram_end - 0x40080000`.
- **S3 ceiling:** the S3's `memory.ld` gives `dram0_0_seg` as
  `(0x403CB700 - (0x40378000 - 0x3FC88000)) - 0x3FC88000` = 0x53700 =
  341,760 from 0x3FC88000, with IRAM sharing it (`.dram0.dummy` 81,920).
  Used is `_bss_end - 0x3FC88000`.
- PlatformIO divides by 327,680 and, on the S3, leaves out the 81,920 of
  IRAM, so it understates all four; on the ESP32-CAM it says 53.7% of a
  board that is at 97.3%.
- **The ESP32-CAM's IRAM is the next wall after DRAM, and nobody has
  looked at it.** 6,764 bytes free. The revision-1 PSRAM cache workaround
  (the profile has no revision minimum, because the bench chip is a
  D0WDQ6 rev 1.0) costs 23,484 bytes of IRAM against the Freenove. Not
  growing (dev.0 and dev.1 are identical), but anything that adds
  `IRAM_ATTR` code or an IRAM-safe driver option on that board will fail
  to link with `iram0_0_seg overflowed`. The lever if it ever bites is
  `CONFIG_ESP_WIFI_IRAM_OPT=n` ("more than 10Kbytes of IRAM", per its
  Kconfig help), at some Wi-Fi throughput this board does not use.

## 3. The flash set: items 1, 2, 3 and 5

All four are Kconfig lines in `sdkconfig.defaults`, so every board gets
them at once. The per-board layer files do not need touching. PlatformIO
only watches `sdkconfig.defaults` itself for changes, so delete the
generated `sdkconfig.<env>` files after the edit and check each one says
what was asked, as CLAUDE.md already warns.

### 3.1 `CONFIG_NEWLIB_NANO_FORMAT=y`: 69.5 KB on every board

| board | image before | after | saved |
|---|---:|---:|---:|
| WROOM | 1,291,056 | 1,221,584 | **69,472** |
| Freenove | 1,363,888 | 1,294,400 | **69,488** |
| ESP32-CAM | 1,417,616 | 1,347,680 | **69,936** |
| S3 | 1,328,592 | 1,259,168 | **69,424** |

- **Where it comes from:** `libc.a` (113,484 on the ESP32-CAM map) is
  replaced by `libc_nano.a` (44,002): the full `vfprintf`/`vfscanf` family
  and the floating-point conversion code behind them. Static DRAM does not
  move.
- **The second reason to take it is the stack.** The full `_vfprintf_r`
  opens with `entry a1, 800`; nano's `_vfiprintf_r` with 160. Every
  `fprintf` into `users.txt`, `mail.dat`, `FILES.BBS` or `system.cfg` sits
  at the bottom of the BBS task's deepest chains (§6), and the camera
  worker's survey writes `FILES.BBS` the same way. About 640 bytes of
  headroom on each, for nothing.
- **What it gives up:** 64-bit integer formats (`%lld`, `%llu`),
  floating-point formats, and positional arguments (IDF 5.3.1
  `newlib/Kconfig`, `NEWLIB_NANO_FORMAT` help). Searched in `src/`: **one
  use, `plugins/camera.cpp:1605`**, `"Oldest kept %04llu-%02llu-%02llu"`,
  which would print garbage in CAMERA's output under nano. It has to change
  to 32-bit arguments in the same commit (the date parts fit a `unsigned`).
  No `%f`, no `%z`, no positional arguments anywhere else; `%*s` width
  arguments are supported. IDF's own log lines that print a 64-bit value
  will print wrongly on the serial console, which is cosmetic.
- **Risk:** low, and the failure is quiet: a `%llu` added later prints
  nonsense rather than failing to build. A three-line check in
  `tools/release.py` (refuse `%ll`, `%j`, `%L`, `%f`, `%e`, `%g` in
  `src/`) makes it loud.
- **How you would know it went wrong:** CAMERA's "Oldest kept" line; and
  `host/` is glibc, so the host tests cannot see it.

### 3.2 Wi-Fi SoftAP and Enterprise off: 43.7 KB, nothing lost

`CONFIG_ESP_WIFI_SOFTAP_SUPPORT=n` and `CONFIG_ESP_WIFI_ENTERPRISE_SUPPORT=n`.

- **Measured on the ESP32-CAM:** image −43,728 (`libnet80211.a` −26,578,
  `libwpa_supplicant.a` −15,819, the rest small), static DRAM −104.
- **What it gives up: nothing the firmware can reach.** The board only ever
  calls `esp_wifi_set_mode(WIFI_MODE_STA)` (`main.cpp:229`), Improv runs
  over the serial port, and a captive portal was declined for good (Rob,
  2026-09-22). Enterprise (802.1X) needs an identity and usually a
  certificate, and nothing in the firmware or CONFIG wifi sets either, so a
  WPA2-Enterprise network cannot be joined today whether the code is
  linked or not.
- **Risk:** very low. **How you would know:** the image stops joining a
  network it joined before, which cannot happen for a network CONFIG wifi
  can describe.

### 3.3 `CONFIG_LWIP_IPV6=n`: 26 KB and 1.8 KB, and the 1.0.0 report was wrong about the cost

- **Measured on the WROOM:** image −26,240, static DRAM −1,784 (was
  estimated at 1,393 and 13.8 KB).
- **The 1.0.0 report called this caller-visible. It is not.** Every
  socket the firmware opens is `AF_INET`: the listener (`bbs.cpp:186`), the
  backup window (`backup.cpp:144`) and announce (`announce.cpp:666, 780`).
  Nothing calls `esp_netif_create_ip6_linklocal()` (searched in `src/` and
  in the managed components) and `CONFIG_LWIP_IPV6_AUTOCONFIG` is off, so
  the interface never has an IPv6 address to be called on. Every board
  shipped so far has been IPv4-only in practice.
- **What it gives up:** an IPv6 listener later needs this back plus the
  code for it. The directory's `/64` rules are server-side and unaffected.
- **Risk:** low. The measurement build linked with mDNS and everything
  else unchanged.

### 3.4 Silent assertions: 60.6 KB flash and 1.5 KB of static DRAM

`CONFIG_COMPILER_OPTIMIZATION_ASSERTIONS_SILENT=y`.

- **Measured on the ESP32-CAM:** image −60,640, static DRAM −1,512 (the
  expression, function and file strings of asserts in IRAM code live in
  DRAM). Paths are already short (`COMPILER_HIDE_PATHS_MACROS=y`), so this
  is mostly the call sites themselves.
- **What it gives up:** a failed `assert()` or `ESP_ERROR_CHECK` aborts
  with an address instead of printing the expression, file and line. The
  panic backtrace is still printed and `monitor_filters =
  esp32_exception_decoder` still turns it into lines, **provided the ELF
  that matches the image is at hand.** `tools/release.py` keeps no ELFs
  today (searched), so a crash log pasted by a sysop running a release
  can only be decoded if the release's ELFs are archived somewhere. That
  is true of every panic already; this makes it true of assertion
  failures as well.
- **Risk:** no behaviour change on a working board. Sysop-visible only on
  a crash.

## 4. The camera boards' RAM: item 4, `.bss` in PSRAM

### 4.1 What was measured

The variant built on the ESP32-CAM profile:

- `sdkconfig.defaults.espcam`: `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y`
  and `CONFIG_SPIRAM_IGNORE_NOTFOUND=n`. The second is forced: IDF 5.3.1's
  `IGNORE_NOTFOUND` "depends on ... !SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY"
  (`esp_psram/Kconfig.spiram.common:16`), because symbols are placed in
  PSRAM at link time.
- `core/bbs.cpp:151`: the section attribute on the singleton,
  `static Bbs bbs;` placed in `.ext_ram.bss` (what `EXT_RAM_BSS_ATTR`
  expands to).
- A linker fragment mapping the camera driver's JPEG encoder object into
  PSRAM with IDF's own `extram_bss` scheme (the one `esp_wifi/linker.lf`
  defines), and `LDFRAGMENTS` on the component in `src/CMakeLists.txt`.

Result, off the ELF: `_bss_end` 0x3FFDAF48 → 0x3FFBD560. **Static DRAM
175,944 → 54,624, free 4,792 → 126,112.** `.ext_ram.bss` is 121,392:

| moved to PSRAM | bytes | how |
|---|---:|---|
| `Bbs::instance()::bbs` (12 sessions, the backup service, everything the singleton holds) | 97,996 | the attribute |
| jpge's statics (`m_huff_codes` 4,096, `huff_code` 1,028, `m_huff_val` 1,024, `m_huff_code_sizes` 1,024, quantisation 512, the rest) | 8,014 | the fragment |
| `libnet80211.a` .bss | 8,405 | automatic with the option |
| `liblwip.a` .bss | 4,122 | automatic |
| `libpp.a` .bss | 1,444 | automatic |
| `libwpa_supplicant.a` .bss | 1,321 | automatic |
| **total** | **121,302** | |

The Freenove carries the same symbols at the same sizes, so the same
figure applies there (not built separately).

Because `_heap_start` is `_bss_end`, **all of it arrives as internal
heap.** From the ESP32 heap layout (`heap/port/esp32/memory_layout.c`),
the internal 8-bit heap at boot is 156,008 bytes on the ESP32-CAM today
and would be 277,328.

### 4.2 Is it safe? Checked against the IDF source, not assumed

- **Flash writes from PSRAM buffers are handled.** External RAM is
  unreachable while the flash cache is off, but `esp_flash_write` copies a
  buffer that is not in DRAM through an internal bounce buffer before it
  disables anything (`spi_flash/esp_flash_api.c:1022-1050`). LittleFS and
  newlib buffer everything on the way anyway.
- **No atomics or locks in `Bbs`.** On the ESP32, compare-and-swap does not
  work on external RAM. The only `std::atomic`s in `src/` are the camera's
  (`g_sizeFound`, `Job::ph`, `g_sensor`), all outside `Bbs`, and they stay
  internal. `Bbs` holds no semaphore or spinlock.
- **No interrupt handler in the app touches it.** No `IRAM_ATTR`, no ISR
  in `src/`.
- **No DMA into a `Session`.** Sockets copy into pbufs, the SD drivers use
  a bounce buffer for a destination that is not DMA-capable, the RMT frame
  (`g_pix`) is not in `Bbs`.
- **Zero-initialised**, as `.bss` already is: the Kconfig help says so, and
  `Bbs` is a function-local static constructed at first call, after PSRAM
  is up.
- **The revision-1 chip** on the bench ESP32-CAM needs the PSRAM cache
  workaround, which that profile already compiles everything with.

### 4.3 What it gives up

- **`SPIRAM_IGNORE_NOTFOUND`.** Today a camera image flashed onto a board
  without working PSRAM "boots as a plain BBS rather than panicking in a
  loop" (the layer files' own comment), and the camera plan relied on it
  ("Wrong image either way still boots"). The web installer cannot tell
  the WROOM, the Freenove and the ESP32-CAM apart (all `chipFamily`
  ESP32), so a wrong pick is possible. Afterwards: the image panics at
  boot, over and over, until the right image is flashed. /install still
  works on a board in that state, so it is recoverable, but it is a worse
  failure, and a camera board whose PSRAM fails in the field goes from
  "no camera" to "no board".
- **The session pool in cached PSRAM.** Espressif's own words for 5.3.1:
  frequently used variables are "almost as quick" as internal RAM through
  the cache, but beyond 32 KB the cache runs out and "speeds will fall
  back to the access speed of the external RAM", pushing flash-cached code
  out as it goes (external-ram guide). The pool is 88 KB and the loop
  touches every live session every pass. **This is the one thing in the
  report that could reach a caller**, as loop time, and Rule no. 1 makes it
  a blocker if it regresses.

### 4.4 How to know, and the two fall-backs

Before shipping: on the Freenove, the same session load before and after
(a DASH open, several callers typing, a YMODEM transfer, a snap), and SYS's
loop average, loop worst and slow-pass count. `tools/benchmark.py` is the
right tool when it exists.

If the loop regresses:

- **Variant B, without the pool: 23,306 bytes** (jpge plus the four IDF
  libraries), still internal heap one for one, and no session data in
  PSRAM. It still costs `IGNORE_NOTFOUND`.
- **Variant C, which keeps `IGNORE_NOTFOUND`: 97,996 bytes.** Construct the
  singleton once at boot into storage from `heap_caps_malloc(MALLOC_CAP_SPIRAM)`,
  falling back to internal if there is no PSRAM (which fits, since the
  static it replaces is the same size). Allocated once before the loop
  starts, never freed, so the loop still never allocates; but it is a
  boot-time allocation rather than a static, and that is an architecture
  decision for Rob, not a sizing one. It does not move jpge or the IDF
  libraries.

One detail for whoever builds A or B: the linker fragment must be wrapped
in `if ESP_ALLOW_BSS_SEG_EXTERNAL_MEMORY = y:` the way
`esp_wifi/linker.lf:126` does it, or the WROOM and S3 builds will be asked
to place jpge in a memory region they do not have. (The attribute on its
own is harmless on the WROOM: `.ext_ram.bss` maps to `dram0_bss` when the
option is off, `esp_system/app.lf`.)

### 4.5 The S3, for 1.2.0

The S3's layer has no `IGNORE_NOTFOUND`, so the same attribute costs it
nothing but the latency question, and would add 98 KB to an internal heap
the SSH phase will want for per-session buffers. Not needed today (92 KB
static free); worth doing as part of the SSH phase's budget rather than
before it.

## 5. Internal heap on the camera boards

### 5.1 Where the ESP32-CAM's goes (estimate, reasoning shown)

The bench: about 9,159 free and 8,535 lowest with the camera up. The heap
available at boot, from the layout and `_heap_start`, is 156,008 on the
ESP32-CAM (157,464 on the Freenove, 168,944 on the WROOM), so about 147 KB
is in use at that moment.

| consumer | bytes | source |
|---|---:|---|
| camera DMA block | 32,768 + descriptors | esp32-camera's ESP32 JPEG path, the camera plan §4 |
| Wi-Fi static RX, 10 | ~16,000 | Kconfig "approximately 1.6KB" each |
| Wi-Fi static TX, 10 | ~16,000 | forced static by `SPIRAM_USE_MALLOC`; the WROOM allocates TX as it sends |
| BBS task stack | 12,288 | `BBS_TASK_STACK` |
| camera worker stack | 8,192 | `kWorkerStack` |
| cam_task stack | 4,096 | `CAMERA_TASK_STACK_SIZE` |
| IDF task stacks | 20,224 | tcpip 3,072, mDNS 4,096, esp_timer 3,584, event 2,304, timers 2,048, idle 2×1,536, IPC 2×1,024 |
| task blocks and per-task state | ~5,000 | about 400 a task, estimate |
| **named** | **~114,600** | |
| **not attributed** | **~32,000** | the Wi-Fi driver's own task (its size is inside the closed library), its state, three LittleFS mounts, chat's history (3,120), sockets, queues, esp_netif, mDNS, fragmentation |

The 32 KB nobody can name is the part to measure rather than argue about:
one `heap_caps_print_heap_info(MALLOC_CAP_INTERNAL)` on the console, or a
per-task stack high-water list in SYS, settles it in an evening.

### 5.2 What buys it back, biggest first

1. **Item 4: +121,302** (§4). Nothing else on the list is within a factor
   of ten of it.
2. **Item 6: Wi-Fi static TX 10 → 6, about 6.4 KB.** The Freenove already
   measured 16 → 10 on both RX and TX as "about 19 KB back" for twelve
   buffers, which is the 1.6 KB each the Kconfig help gives. A frame past
   the sixth waits in the 32-deep cache TX queue
   (`ESP_WIFI_CACHE_TX_BUFFER_NUM`, in PSRAM) rather than being dropped.
   This board sends a few hundred bytes at a time; YMODEM is stop and wait
   in 1 KB blocks. **Honest throughput cost:** a burst of screen redraws to
   ten callers at once queues a little longer before the radio takes it,
   and a bulk sender would be slower; nothing on this board is a bulk
   sender. **Measure:** a YMODEM download's time and DASH with ten callers,
   before and after. Range is 1 to 64 (`esp_wifi/Kconfig:94`), so 6 is
   kept, not clamped.
3. **Also on both camera layers, no memory claim:** `CONFIG_ESP_WIFI_RX_BA_WIN`
   is 16 there (the `TRY_ALLOCATE_WIFI_LWIP` default), against 10 static RX
   buffers. The Kconfig help recommends static RX at or above the window.
   An access point may send a 16-frame aggregate into 10 buffers. 6 is the
   WROOM's value. It is a consistency fix, and cheap to take with item 6.
4. **Camera worker stack 8,192 → 6,144: 2,048, during a snap only.** Its
   deepest chain by frame sizes is `worker` 1,104, `survey` 720, a lambda
   288, `files::photoDescDrop` 288, then `fprintf` (800, or 160 with item
   1) and FatFs. The bench measured 2,008 free of 6,144 before (4,136
   used), which is why it went to 8,192. With item 1 that chain is about
   640 shallower. **Read the console's `camera: worker stack N free` line
   after an OV2640 UXGA snap with levels and a GC0308 snap; if the worse of
   the two is 3.5 KB or more, 6,144 is safe.** It also lowers
   `kSnapInternal`, so a snap is refused less often.
5. The BBS task stack: see §6. Not recommended to trim.

`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` (16,384) could push medium `malloc`s
into PSRAM and is left alone: nothing large sits in the 4 to 16 KB band
that could be named, so the gain is unknown and the heap dump above comes
first.

### 5.3 The S3: item 7

The S3's layer takes the `TRY_ALLOCATE_WIFI_LWIP` defaults: 16 static RX,
16 static TX, window 16 (generated `sdkconfig.ws_s3_lcd147`), about 51 KB of
internal RAM for the radio. The camera layers' 10/10 would return about
19 KB, by the Freenove's own measurement. The S3 is not short today (77,739
free, 68,031 lowest at dev.8); it is two lines to take before SSH starts
asking for heap.

## 6. Stacks

### 6.1 The BBS task, 12,288

- It is heap, not static, and on the camera boards it is **internal**
  heap: task stacks are allocated internal even with PSRAM.
- No board reading of it since 1.1.0 was available to this report. The
  board has the instrument: SYS "Stack free ... least of 12,288" and the
  "bbs: stack low" console lines.
- From the frames in this build: the largest is `showMessage` 2,128
  (192 of it the `body[kBodyMax + 1]` the composer can never fill, 0.22.0
  report finding 4.3, still true), then `cmdRestore` 1,376, `rewrite`
  1,152 (now including its `UserRec` local), `readClient` 1,152,
  `users::range` 1,056. The host measured restore at 13,096 host bytes,
  and host frames run about twice the target's, so about 6.5 KB on the
  board: roughly 5.5 KB of margin at 12,288. Item 1 adds about 640 to
  every chain that ends in `fprintf`.
- **Recommendation: hold at 12,288.** Trimming it would give the camera
  boards 2 KB of internal heap, which item 4 makes pointless and item 6
  beats without touching a stack. If item 4 is declined, read SYS on UHQ
  or TRA after a week on 1.1.x first; below 5 KB least-free, leave it.

## 8. Flash items that cost something, and the don'ts

### 8.1 Item 8: the lights plugin off the camera profiles, ~21 KB

From the ESP32-CAM map: `lights.cpp.o` 11,547 of flash and 213 of DRAM,
`libesp_driver_rmt.a` 9,583 and 89. The ESP32-CAM has no NeoPixel and
almost no free pins; the Freenove has none on board and three free pins.
But the camera's pixel-mode flash shares the lights' drive pin
(`pinShares`), so taking lights off also takes that option away. A feature
cut for sysops who wire a pixel to a camera board; Rob's call, and not
needed if items 1 to 5 are taken.

### 8.2 Item 9: IDF log level WARN, 13.3 KB

`CONFIG_LOG_DEFAULT_LEVEL_WARN=y` with `LOG_MAXIMUM_EQUALS_DEFAULT=y`:
image −13,296 on the ESP32-CAM, static −48. The firmware's own
`plat::log` is `printf` and is untouched; what goes is IDF's INFO lines,
including "PSRAM found" and the Wi-Fi join lines the bench reads. Last,
and only if flash gets tight again.

### 8.3 Do not

- **WPA3 off** (`ESP_WIFI_ENABLE_WPA3_SAE=n`): measured 29,648 flash and
  232 static, and a board then cannot join a WPA3-only network, which a
  sysop would meet as "my new router will not take it". It also does not
  take mbedTLS out (`ESP_WIFI_MBEDTLS_CRYPTO` stayed selected), and the
  signed OTA in the queue will want ECDSA from mbedTLS anyway.
- **The camera worker's stack in PSRAM.** IDF 5.3.1's ESP32 help for
  `SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY` allows it only for a task that
  "does not call on ROM code in any way", and the worker's decode is the
  ROM's TJpgDec.
- **`BBS_TL_BYTES` below 3,072.** The C64 type-ahead case, unchanged.
- **Wi-Fi IRAM optimisations off for RAM's sake.** On the ESP32, IRAM
  freed does not become byte-addressable heap. Keep it for the ESP32-CAM's
  IRAM ceiling (§1) if that ever bites.
- **`SPIRAM_MALLOC_RESERVE_INTERNAL` below 40,960.** It is what keeps the
  camera's 32 KB DMA block in one piece; the layer files explain why 32 KB
  was not enough.

## 9. Quietly growing

- **Flash is the trend now, not DRAM.** +103 KB WROOM in 1.1.0; +8.4 KB on
  the ESP32-CAM in dev.1. The ESP32-CAM has 155 KB left. Items 1+2+3+5 put
  it at 355 KB.
- **The camera boards' static DRAM drops about 120 bytes per camera
  feature**, mostly in `g_job` (968 → 1,016, initialised, so it is also

- **The ESP32-CAM's IRAM, 6,764 free.** Flat, but the least headroom of

## 10. Reproducing this

```sh
TC=~/.platformio/packages/toolchain-xtensa-esp-elf@13.2.0+20240530/bin
ELF=.pio/build/esp32cam_aithinker/firmware.elf

# the ceiling, from the generated linker script
grep -n "dram0_0_seg\|iram0_0_seg" .pio/build/esp32cam_aithinker/memory.ld

# the only static DRAM number that means anything (S3: minus 0x3FC88000, of 341,760)
$TC/xtensa-esp32-elf-nm.exe $ELF | grep -E ' (_bss_end|_iram_end)$'

# every DRAM symbol, biggest first, filtered by address (nm marks flash rodata d/D too)
$TC/xtensa-esp32-elf-nm.exe -S --size-sort --radix=d -C $ELF \
  | awk '$1+0 >= 1073414144 && $1+0 < 1073594880' | sort -k2 -rn | head -40

# a function's static frame: the entry immediate (hex above 255, parse with int(x, 0))
$TC/xtensa-esp32-elf-objdump.exe -d -C --no-show-raw-insn $ELF | grep -A1 '<_vfprintf_r>:'
```

The measurement variants were Kconfig lines appended to the board's layer
file (`sdkconfig.defaults` for the WROOM, `sdkconfig.defaults.espcam` for
the ESP32-CAM, and so on), the generated `sdkconfig.<env>` deleted, one
`pio run -e <env>`, and `git checkout -- .` afterwards. The generated file
was checked each time to say what was asked, because an out-of-range value
reverts silently.

Traps, carried and new:

1. `nm` marks flash `.rodata` as `d`/`D`; filter every RAM figure by
   address.
2. ld files the whole merged string pool under the first object that
   contributes one (`backup.cpp.o` here). Per-object rodata from the map
   double-counts it; a map sum over `.dram0.*` also comes out about 3.6 KB
   over `_bss_end` for the same kind of reason. Use `_bss_end` for totals
   and the map only for per-library deltas.
3. `objdump` prints `entry` immediates over 255 in hex.
4. **New:** PlatformIO's RAM line on the S3 leaves out the 81,920 bytes of
   IRAM that share the segment, so it understates the S3 as well, in a
   different way from the ESP32.
5. **New:** a heredoc turns `\n` inside a Python string into a real
   newline. Measurement scripts here were written with the Write tool for
   that reason, per the standing rule.
