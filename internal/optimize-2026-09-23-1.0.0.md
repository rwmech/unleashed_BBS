# Optimisation report: µnleashed BBS 1.0.0

Date: 2026-09-23
Previous reports: `internal/memory-2026-09-22-0.22.0.md` (0.22.0),
`internal/memory-2026-09-22.md` (0.21.1), `internal/optimize-2026-09-20.md`
(0.17.2).

Nothing was built, changed, committed or flashed. Every figure is from
`.pio/build/esp32dev_release/firmware.elf` (2026-09-23 14:06) and its map.
The `esp32dev` build directory no longer exists; the release environment
differs only by `-DBBS_RELEASE`, which gates `include/secrets.h` in
`main.cpp`, and CHANGELOG 0.22.3 records the same 176,880 for the developer
build, so the two are the same board as far as DRAM goes.

## 0. The headline

**176,880 of 180,736 bytes. 3,856 free. 97.9% of the real ceiling.**
PlatformIO would call this 54.0%.

**1.0.0 cost nothing over 0.22.3, and 0.22.3 cost 24 bytes over 0.22.1.**
The 880 bytes spent since the last report all went in 0.22.1, and 834 of
them are one decision, the Wi-Fi network moving into `system.cfg`, paid
four times over because `SysConfig` exists four times in DRAM (§3). The
first-boot setup flow in 0.23.0 cost **zero**: `Session::setupStage` landed
in an existing padding hole, which is exactly what the 0.22.0 report asked
for.

**The trend, nine measurements** (all `_bss_end − 0x3FFB0000`):

| build | static DRAM | headroom | what moved |
|---|---:|---:|---|
| 0.17.2 (09-20) | 146,376 | 34,360 | |
| 0.21.1 | 175,960 | 4,776 | forums, composer, identity: +29,584 |
| 0.21.3 | 170,232 | 10,504 | `seen` and `g_cfgWas` hashed: −5,728 |
| 0.21.5 | 174,864 | 5,872 | `BBS_COMPOSE_MAX` 1152 → 1536: +4,632 |
| 0.21.9 | 175,488 | 5,248 | +624 |

| 0.22.1 | 176,856 | 3,880 | Improv 336, Wi-Fi keys ×4 copies 400, `s_ssid`/`s_pass` 98: **+856** |
| 0.22.3 | 176,880 | 3,856 | two kept LittleFS figures: +24 |
| **1.0.0** | **176,880** | **3,856** | **0** |

Since 0.21.5 the board has spent 2,016 bytes across eight versions, against
29,584 in the one milestone before that. The rate is now about 250 bytes a
version. **Nothing has been recovered since 0.21.3**, and the three savings
that report and the two after it recommended are all still on the table,
unchanged, and are now the whole of this report's top five.

**What 1.0.1 needs, and which pool it comes from.** This is the point the
brief turns on and it is worth stating before the ranking:

- **The announce payload 512 → 768** is static: `g_body` +256 and
  `g_request` (`kBodyMax + 256`) +256, **+512 of the 3,856**. Finding 6
  makes it cost −256 instead.
- **A larger BBS task stack is heap, not static.** `xTaskCreatePinnedToCore`
  allocates the stack through `pvPortMallocStack`, which IDF 5.3.1 defines
  as `pvPortMalloc` (`freertos/FreeRTOS-Kernel/include/freertos/portable.h:191`).
  8,192 → 12,288 costs **4,096 of heap and 0 of the 180,736**. But
  `_heap_start` is `_bss_end`, so **every static byte recovered below is a
  heap byte gained**, one for one. The savings fund the stack that way.

**One finding changes how the board behaves for callers**: `CONFIG_LWIP_IPV6=n`
(carried, 1,393 bytes) takes the board off IPv6. Not recommended without
Rob deciding that is fine. The pool-of-six variant of #3 adds a refusal
message for a seventh simultaneous form. Nothing else here is visible to a
caller.

## 2. The five the brief asked about

### 2.1 `BackupService::exp_` and `imp_` as a union: 3,872, fourth time

Unchanged: `Bbs::backup_` is 12,192 at offset 4 of the singleton;
`ZipExport exp_` 5,016 at 2,624, `ZipImport imp_` 3,872 at 7,640, both
resident. The 0.22.0 report said "if the next milestone report says this
again, the finding is not the union". It is being said again, so here is
the invariant re-verified against 1.0.0's `backup.cpp` line by line rather
than asserted:

- **One client at a time**: a second `accept()` while `cfd_ >= 0` gets a
  503 and is closed (`backup.cpp:238-243`).
- **A request is only routed from `St::Headers`** (`readClient`, :258-268).
  In `Body` the bytes go to the staging file; in `Extract` and `Approve`
  anything received is ignored (:280). So a download cannot be asked for
  while an upload is staged.
- **`exp_` is live from `route()` (`scan`, :377) through `SendZip`
  (`produce`, :322) to `Reply`.** **`imp_` is live from `Body` (`open`,
  :296) through `Extract` (`step`, :158) and `Approve` to `decide()`
  (`apply`/`discard`, :486/:493).** The two ranges are disjoint by the
  state machine, and `St` is one enum.

**The one trap, named.** `dropClient` (:465-477) calls `imp_.discard()`
gated on the upload states and then `exp_.abort()` and
`exp_.dropSnapshot()` **unconditionally**. Under a union those two must be
gated the same way (`st_ == SendZip`, or "whichever member is live"), or
`abort()` runs on bytes that are a `ZipImport`. That, plus a placement-new
or a tagged storage block because both classes have constructors, is the
whole change. **Risk: low, one file.** `test_backup` on the host exercises
both directions and would show a corrupted restore.

### 2.2 The 22 `static UserRec` scratch buffers: 10,824, and the stack reading answers the question the wrong way

Still 22 × 492 (`bbs.cpp` 7, `bbs_users.cpp` 7, `bbs_sysop.cpp` 3,
`users.cpp` 8; nm lists every one). The 0.21.1 and 0.22.0 reports both said
"measure first"; `SYS` was given the measurement in 0.21.3; Rob read it on
0.22.1: **1,440 bytes free, least ever, of 8,192.**

**That figure is bytes, verified.** `platform_esp32.cpp:150` says
`uxTaskGetStackHighWaterMark` "reports in WORDS on Xtensa" and multiplies by
`sizeof(StackType_t)`. In the installed 5.3.1 Xtensa port `portSTACK_TYPE`
is `uint8_t` (`portable/xtensa/include/freertos/portmacro.h:88`), so the
kernel's `ulCount /= sizeof(StackType_t)` (`tasks.c:4805`) divides by one
and the mark is already bytes; the board's multiply is by one too. **The
comment is wrong and the code is right**, which is the harmless version of
a pattern this project has been bitten by four times, and it is worth
fixing the comment before somebody "corrects" the code to match it.

So the deepest call since boot used 6,752 of 8,192. **Which path is not
known.** Summing the largest static frames along the plausible chains (frame
sizes read from each function's `entry a1, N`):

| chain | frames | static sum |
|---|---|---:|
| mail send: `onKey` 128 → `chat::onKey` 656 → `mailSend` 1,232 → `mailRewrite` 832 → `_vfprintf_r` 800 | | ~3,650 |
| restore apply: `onKey` → `decide` 496 → `ZipImport::apply` 1,648 → `extract` 848 → `_vfprintf_r` 800 | | ~3,800 |
| file approve: `files::onKey` 1,216 → `doApproveQuiet` 768 → `setDesc` 640 → `_vfprintf_r` 800 | | ~3,550 |
| forum read: `forums::onKey` → `showMessage` 2,128 → `codes::row` 128 → Term | | ~2,600 |
| account save: `formSave` 144 → `users::update` 32 → `rewrite` 656 → `writeRecord` → `_vfprintf_r` 800 | | ~1,750 |

**Every static sum is 2 to 3 KB short of the measured 6,752.** Two things a
static sum cannot see are on the task stack: the exception frame an
interrupt pushes onto the *interrupted task's* stack before it switches to
`port_IntStack` (`XT_STK_FRMSZ`, `xtensa_context.h:195`), and the flash
write chain under every `fprintf` to LittleFS (newlib's `__sfvwrite`, the
VFS, `lfs_file_write` → `lfs_bd_prog` → `esp_flash_write`, which runs on the
calling task with the cache disabled). **A stack audit done by reading
frames will undercount by that much; the board's own number is the one to
trust.** That is an inference from the gap, not a measurement of the
chain.

**What the conversion adds.** Three records nest on every account write:
`formSave`/`cmdPassword`/`markAccount`/`rememberStaff`/`saveCallStats`
(one) → `users::update` (`probe`, on a rename) → `rewrite` (`u`). As locals
that is **up to 1,476 bytes** on a path that already carries `rewrite`'s
656 and the flash write chain. If the 6,752 mark was set by an account
write, conversion at 8,192 lands within a few hundred bytes of the canary.
If it was set by mail or a restore, conversion changes nothing. Nobody
knows which, and "probably fine" is the phrase that precedes a reboot.

**So the order is the finding:**

1. **Log the mark at every new low, with the path.** `Bbs::tick` already
   logs a slow pass with its phase and `Session::doing` (`bbs.cpp:427-442`);
   the same few lines around `plat::stackFree()` name the deepest chain in
   one evening on the board. This is the audit; reading frames is not.
2. **`BBS_TASK_STACK` 8,192 → 12,288**, +4,096 heap, before anything else
   in 1.0.1. `CONFIG_FREERTOS_CHECK_STACKOVERFLOW_CANARY` is on, so an
   overflow is a panic and a reboot log line rather than silent corruption,
   which is the loud failure the 0.21.1 report promised. Whether 12,288 or
   16,384, decide from step 1 and one `MEM` reading (§4).
3. **Then convert, in two tranches, reading `SYS` between.** `users.cpp`'s
   eight first (3,936: five are leaves, `update`/`retire`/`add` nest two
   deep), then the fourteen in `bbs*.cpp`. `formSave`'s three `cur` in
   disjoint scopes become one stack slot.

**What it gives up:** stack, on paths the board can now name. **How you
would know:** a reboot with the canary's message, and `SYS` reading under
1,000 after a session that writes accounts.

One related frame, unchanged since 0.21.1 finding 4.3: `showMessage`'s
2,128 holds `body[kBodyMax + 1]` = 1,729 for bodies the composer caps at
1,536. 192 bytes of the largest frame on the task can never be filled.

### 2.3 Form context and composer share storage: 11,856, re-checked against 1.0.0

Per session: `compose[1537]` against `edit` 492 + `fields[16]` 320 + `form`
176 = 988. A union is 1,537, saving 988 × 12 = **11,856**; `pwA/B/C` (99)
are form-or-login only, **1,188** more on the same invariant; the pool of
six for the form triple, no invariant, a refusal for the seventh: **5,928**.

The exclusivity was re-verified for 1.0.0, since 0.23.0 added a flow that
opens a form from outside the usual entry points:

- `grep '\.(form|fields|edit|pwA|pwB|pwC)\b' src/plugins/` is **still
  empty**. No plugin touches the form storage.
- `s.compose` is written by chat (mail compose), forums (post), info (page
  edit and the paged read) and cleared in `openSession`. All three plugin
  uses are under a plugin claim (`SState::Plugin`, or `List` through
  `startPluginList` for info's reader).
- `s.edit` outside forms is read in the core only at login
  (`bbs.cpp:1228-1640`: lookup into it, then `dayKey`, `level`, `calls`,
  `lastCall`), which completes before any plugin can own the session, and
  is re-read fresh by every form (`cur` statics, the 0.8.0 review).
- **The 0.23.0 setup flow** asks for the sysop password through the line
  editor at the prompt and then opens `CONFIG staff` as an ordinary
  `SState::Form` (`bbs.cpp:1774-1785`, `bbs_users.cpp:270`). It adds no
  new writer of either buffer.

The guard the 0.21.1 report asked for is unchanged in shape: a `uint8_t
scratchOwner` on `Session`, set on entry to either subsystem, checked on
entry to the other, **refuse rather than reuse**. Without it this is the
"one name, two meanings" bug this project has already had twice
(`owns()`, `Forum::unread`). With it, it is the only entry on this page big
enough to change what the board can afford next: 11.8 KB is more than every
version since 0.21.5 has spent put together, five times over.

**If only one of #2 and #3 is taken, take #2**, for the reason the 0.21.1
report gave: its failure is a panic and its guard is a number on `SYS`.

### 2.4 Reorder `Session`, `UserRec` and `SysConfig`: about 520, not 600

From `ptype /o` on the 1.0.0 ELF:

- `Session` has **23 bytes of holes at its own level** (after `ip` 1,
  `setupStage` 1, `loggedIn` 1, `idleWarned` 2, `rawInput` 1, `watchSecs`
  1, `countdown` 3, `landing` 3, `level` 1, `histPos` 3, `term` 3, `mb` 3).
  The struct holds pointers so its size rounds to 4: 7,372 − 23 = 7,349 →
  7,352, **20 per session, 240 across twelve**.
- `UserRec` has 11 (after `profile` 2, `retired` 3, `pass` 1, `calls` 2,
  tail 3): 492 → 484, **8 × 34 copies = 272**. `users.txt` is text, so the
  layout is not a file format.
- `SysConfig` has 2 (after `sysopDefault`, `guestEnabled`): 410 → 408,
  **× 4 copies = 8**.
- `Timeline`'s 3 bytes round straight back to 3,484: no gain. The
  `Telnet`/`Detector`/`ScreenPlayer` tails are alignment padding a reorder
  cannot remove.

**~520 total.** The 0.22.0 report's "~600" summed the holes without
rounding each struct back up to its alignment. Zero risk, zero behaviour,
and it is the only entry that costs literally nothing; but it churns the
two structs everything touches, so it wants a commit of its own and a
`ptype /o` afterwards to prove the holes went. `MailRec` and `CallRec` are
on-disk formats with static asserts: leave them.

### 2.5 `serialbridge::g_back` allocated at plugin start: 1,024

`serialbridge.cpp:83`, `char g_back[kScrollback]`, resident on every board;
the plugin is off unless `[plugin:serial]` switches it on. `start()`
(:271-289) already has two failure exits and `stop()` (:291) already tears
down; chat's `g_hist` (`chat.cpp:2873` calloc, `:2899` free) is the
precedent and the fallback wording. Every use is through `keep()`, the
replay at :205 and the reset at :276, so a null check in `keep()` and the
replay covers it. A board that bridges a serial device pays 1,024 of heap
once at start; every other board gets 1,024 of static back. **Risk: low.**
Failure is "serial: no room for the scrollback" and the plugin not
starting, which is the same shape chat already has.

### 2.6 announce: the 768 growth pays for itself

`g_body[512]`, `g_request[512 + 256]` and `g_reply[768]` are 2,048 bytes.
The 1.0.1 growth as written would be 768 + 1,024 + 768 = 2,560, **+512**.

**`g_request` and `g_reply` are never live together**, and this is now
cheaper than the 0.22.0 report said. That report warned that `startPost`
clears `g_reply` "at the start of an exchange" and the clear would have to
move. Reading 1.0.0's `startPost` (`announce.cpp:477-508`): the clear is at
:479-480 and `buildRequest()` is at :501, **after** it, so under aliasing
the clear wipes an empty buffer and then the request is built. `Sending`
(:540-549) drains `g_request` to `g_sent == g_reqLen` before `Reading`
(:551) writes a byte of `g_reply`; `finish()` touches neither; `ANNOUNCE
TEST` (:696) prints `g_body`, which stays separate. One shared buffer, no
ordering change.

Size it honestly while it is open: the 0.21.1 report counted the request
headers at up to 318 bytes, so `kBodyMax + 256` is short by 62 for a
maximal path and host, and `took()` refuses the post rather than sending
it. **`kBodyMax + 320` = 1,088** as the shared buffer: 768 + 1,088 = 1,856
against today's 2,048, **net −192 with the growth included**, and the reply
side gets 1,088 instead of 768 for the badge headers that are coming
(`X-Listing-Reason` alone is 121). The −256 in the summary table assumes
`+256`; use 1,088 and call it −192.

Still there by policy: `g_servers[4]` at 252 each, `kMaxServers` 2 saves
504. One directory exists. Rob's call.

**Every byte added to `SysConfig` costs four**: `g_cfg` (live), `g_scratch`
(`reload`/`trial` parse into it, `sysconfig.cpp:331`), and two static
locals in `ziparc.cpp:676` and `:687` that exist so a restore can validate
the uploaded `system.cfg` and read its `max_users`. All four are in
`.data`, because `SysConfig` has non-zero defaults, so each also costs 410
of flash and a copy at boot.

**The two `ziparc` probes are per-call scratch** (`probe = SysConfig()` at
:678 then parsed and read within the same `extract()` call; `cfgProbe`
likewise at :690-694). `extract()` runs on the BBS task from

from a command, so a call into `syscfg` that parses into `g_scratch` and
hands back the one field `extract()` wants cannot interleave with a CONFIG
save. **820 bytes of `.data` and 820 of flash for about fifteen lines.**
Risk: low; `test_backup` restores a zip with a `system.cfg` in it.

This is the same leverage lesson as `UserRec` × 34 and `Session` × 12, and
it is new: the Wi-Fi keys were the right thing to put in the config, and
they cost 400 bytes for 100 bytes of field because nothing said the struct
was copied four times.

## 4. Heap, because the stack lives there

The BBS task stack is `pvPortMalloc`'d at boot; growing it draws on the
internal heap that begins at `_bss_end`. What is on record:

- 0.8.0: heap free 143,344, minimum 118,268, largest block 110,592, at
  107 KB static.
- 0.17.0: "roughly 78 KB free at boot" at 174.6 KB static, estimated then.
- 0.18.x: **a live board reached 19,736 bytes of minimum free heap and
  restarted on its own** (`sdkconfig.defaults:111`), which is why the lwIP
  send buffer and window went 5,760 → 2,880 per socket and the Wi-Fi
  dynamic buffers 32 → 16. Two later readings: heap low 25,204 and 50,224.
- Since then: **no reading on the board.** `MEM` prints heap free, heap
  low and biggest block; `SYS` prints heap free and low.

So the honest statement is: static grew 2.3 KB since the 78 KB estimate,
the lwIP cuts gave some back, the chat history is 48 × 65 = 3,120 of heap
at plugin start, a mounted card is ~11 KB at mount, and nobody has written
down "Heap low" from a 0.22.x or 1.0.0 board. **One `MEM` reading after a
session with a card, a forum post, a mail and a backup download settles
whether 12,288 or 16,384 is the right stack, and it costs nothing.** The
static savings in §1 add 5,972 to whatever that reading is; the stack at
12,288 takes 4,096 of it back.

Knobs that are heap and not static, unchanged since 0.22.0 and verified in
the generated `sdkconfig.h`: `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM` 10
(1,600 each, `wifi_malloc` at init, not `.bss`), `DYNAMIC_RX/TX` 16,
`RX_BA_WIN` 6, `LWIP_TCP_SND_BUF/WND` 2,880, `LWIP_MAX_SOCKETS` 16. The
static RX pool at 6 would free 6,400 of heap; measure a YMODEM transfer
before trusting it, as the 0.22.0 report said.

Task stacks in this build, all heap: BBS 8,192, mDNS 4,096, main 4,096,
esp_timer 3,584, lwIP 3,072, event 2,304, timer 2,048, idle 1,536 × 2.
`port_IntStack` (3,072, `.data`) is the one static one and is at the
Kconfig floor.

## 8. Reproducing this

```sh
TC=~/.platformio/packages/toolchain-xtensa-esp-elf@13.2.0+20240530/bin
GDB=~/.platformio/packages/tool-xtensa-esp-elf-gdb/bin/xtensa-esp32-elf-gdb.exe
ELF=.pio/build/esp32dev_release/firmware.elf

# the only RAM number that means anything: (_bss_end - 0x3FFB0000) vs 0x2C200
$TC/xtensa-esp32-elf-nm.exe $ELF | grep -E ' _bss_end$'

# every DRAM symbol, biggest first (filter by address: nm marks flash rodata d/D too)
$TC/xtensa-esp32-elf-nm.exe --size-sort -S --radix=d -C $ELF \
  | awk '$1+0 >= 1073414144 && $1+0 < 1073594880' | sort -k2 -rn | head -40

# struct layouts with padding holes
$GDB -batch -nx -ex "set pagination off" -ex "set max-value-size unlimited" \
     -ex "ptype /o struct Session" -ex "ptype /o struct UserRec" \
     -ex "ptype /o struct SysConfig" -ex "ptype /o BackupService" $ELF

# every function's static frame: the entry immediate is the frame size.
# Frames over 255 print in HEX (entry a1, 0x850): parse with int(x, 0), or
# the biggest frames vanish from the list, which is what happened first here.
$TC/xtensa-esp32-elf-objdump.exe -d -C --no-show-raw-insn $ELF \
  | grep -A1 -E '^[0-9a-f]+ <' | grep -oE 'entry\s+a1,\s*\S+'

# stack units: portSTACK_TYPE is uint8_t in this port, so the high water mark is bytes
grep -n 'define portSTACK_TYPE' ~/.platformio/packages/framework-espidf@3.50301.0/components/freertos/FreeRTOS-Kernel/portable/xtensa/include/freertos/portmacro.h
```

Traps carried forward, plus two new:

1. `nm` marks flash `.rodata` as `d`/`D` too. Filter every RAM figure by
   address.
2. GNU ld attributes the whole merged string pool to the first object
   contributing `.rodata.str1.1`; per-object rodata figures from the map
   double-count.
3. **New:** the map prints placed addresses as 16 hex digits
   (`0x000000003ffb...`); a grep for `0x3ff` finds only the unplaced
   archive-member listing at `0x00000000` and returns nothing useful. Walk
   the `.dram0.data`/`.dram0.bss` output-section blocks instead.
4. **New:** objdump prints `entry` immediates over 255 in hex. A `\d+`
   regex silently drops every frame that matters.
